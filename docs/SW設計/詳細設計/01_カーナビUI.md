<a id="dd-1"></a>
## 1. 目的・適用範囲

<a id="note-ref-qml"></a>
タッチパネル上のカーナビ画面を管理する。QML[注1](#note-qml)は画面の表示、Pythonは表示する情報の管理と他ソフトとの通信を担当する。

<a id="note-ref-qt"></a>
画面を作るための仕組みとしてQt[注2](#note-qt)を使う。
<a id="note-ref-pyside6"></a>
PythonからQtを利用し、QMLで作った画面と連携するためにPySide6[注3](#note-pyside6)を使う構成を設計案とする。

対象はホーム、ナビ、Android Auto、カメラ、音楽、車両情報、設定、起動状態、警告表示とする。具体的な画面は[4.1 画面一覧](#dd-41)に記載する。映像取得、位置推定、車体GPIO操作は別担当ソフトの役割とする。

<a id="dd-2"></a>
## 2. 要求仕様・役割

| ID | 要求 |
| --- | --- |
| UI-01 | ナビ未準備でもホーム・カメラを利用可能にする |
| UI-02 | 警告、バックカメラ、駐車サラウンド、通常画面の優先順位を管理する |
| UI-03 | 無効・期限切れの値を数値0や正常表示に置き換えない |
| UI-04 | 外部アプリ停止や通信断でUI全体を停止させない |
| UI-05 | テスラの画面を参考に、余白・簡潔な表示・下部の操作領域を活かしたモダンな自作UIとする。実装していない車両機能は表示しない |

<a id="dd-functions"></a>
### 2.1 機能一覧

機能は「UIが何をできるか」を表す。モジュール名や関数名ではなく、利用者から見える動作とUIの運用上の動作を定義する。

| 機能ID | 機能名 | 実現する動作 | UIの担当範囲・制約 |
| --- | --- | --- | --- |
| [UI-F01](#dd-feature-f01) | UIの起動 | 設定を読み込み、ホームなどの画面を利用可能にする | ナビなどの担当ソフトが未準備でも、UI自体は起動する |
| [UI-F02](#dd-feature-f02) | 通常画面の切替 | ホーム・音楽・車両情報など、選択した画面を表示する | 現在の操作許可と優先表示を確認する |
| [UI-F03](#dd-feature-f03) | ナビ・Android Autoの表示連携 | 対象アプリの起動・表示を要求し、準備状態を表示する | 地図描画・経路案内・Android Auto本体は外部ソフトが担当する |
| [UI-F04](#dd-feature-f04) | 音楽操作・再生状態の表示 | 再生・一時停止・選曲・音量変更を要求し、曲情報と結果を表示する | 音声の再生処理は12 オーディオ連携とその連携先が担当する |
| [UI-F05](#dd-feature-f05) | カメラ映像の表示 | 選択した方向の映像と取得・録画状態を表示する | カメラ取得と録画は06 カメラ表示・録画が担当し、UI終了で録画を止めない |
| [UI-F06](#dd-feature-f06) | 後方映像の優先表示 | 有効なリバースONで後方映像を優先し、有効なOFFで復帰先を確認する | リバースは15 サブコントローラ1後方系から受け取り、信号不明をOFFに置き換えない |
| [UI-F07](#dd-feature-f07) | 車両・運用状態の表示 | 車速・水温・CPU温度・録画状態・位置品質などを表示する | 担当ソフトから受け取る。未取得・期限切れを数値0にしない |
| [UI-F08](#dd-feature-f08) | 警告表示 | 異常の内容と重要度を表示し、利用者による確認を受け付ける | 利用者の確認だけで異常の原因が解消したとは扱わない |
| [UI-F09](#dd-feature-f09) | 設定の変更・保存 | 設定値の編集、適用、取消、確定した利用者設定の保存を行う | 操作許可と適用結果を確認し、秘密情報や未適用の値を保存しない |
| [UI-F10](#dd-feature-f10) | UIの終了 | 新しい操作を止め、設定保存と表示・通信の後片付けを行う | 録画担当ソフトやOS自体の停止とは別の機能とする |
| [UI-F11](#dd-feature-f11) | 駐車サラウンドの表示 | 停止・駐車条件を満たすときに合成映像を表示する | 段階開発対象。合成は08 サラウンドビューが担当し、品質不良時は利用させない |

ドアロック操作とBLE TPMSは初期運用の機能に含めない。画面の種類は[4.1](#dd-41)、操作部品は[4.3](#dd-43)、機能を利用できる条件は[8.1](#dd-81)に記載する。

| [UI-F04](#dd-feature-f04) | ScreenController、ServiceBridge、AppState、QML画面群 | ScreenControllerのhandle_action・on_service_event、ServiceBridgeのsend_command、AppStateのapply_update | 12 オーディオ連携 |
| [UI-F05](#dd-feature-f05) | ScreenController、ServiceBridge、QML画面群、AppState | ServiceBridgeのsubscribe_video・unsubscribe、ScreenControllerのon_service_event | 06 カメラ表示・録画、frame_presenter。AppStateは映像以外の状態を保持する |
| [UI-F06](#dd-feature-f06) | ScreenController、ServiceBridge、AppState、QML画面群 | ScreenControllerのon_service_event・reevaluate_display・restore_previous_screen | 15 サブコントローラ1後方系のリバース通知と06 カメラ表示・録画の後方映像を別々に受信する |
| [UI-F07](#dd-feature-f07) | ServiceBridge、ScreenController、AppState、QML画面群 | ServiceBridgeのsubscribe_state、ScreenControllerのon_service_event・expire_stale_data、AppStateのget_display_data | 車両情報・録画・冷却などの担当ソフト |
| [UI-F08](#dd-feature-f08) | ScreenController、AppState、QML画面群 | ScreenControllerのon_service_event・handle_action、AppStateのapply_update | WarningModel、WarningOverlay.qml |

例えばUI-F04の「再生状態を表示する」動作では、ServiceBridgeが再生状態を受け取り、ScreenControllerのon_service_eventが確認し、AppStateのapply_updateで表示データを更新する。QML画面はその変更を受けて再生状態を表示する。
この一連の動作が「機能」、担当する各構成要素が「モジュール」、各構成要素の中で実行する処理が「関数」である。

<a id="dd-3"></a>
## 3. 内部構成

[2.1](#dd-functions)の機能を実現するため、UIを以下のモジュールで構成する。全体構成は[3.1](#dd-31)、機能ごとの処理の流れは[3.2](#dd-feature-connections)、モジュールツリーは[3.3](#dd-39)、処理順序は[3.4](#dd-38)、モジュール詳細は[3.5](#dd-module-details)、ファイル構成は[3.6](#dd-37)、関数の処理手順は[3.7](#dd-310)に記載する。

| モジュール名 | 担当する役割 |
| --- | --- |
| 起動・終了管理（main_app） | 画面アプリを起動し、必要なモジュールを組み合わせ、終了時に後片付けする |
| 画面切替管理（ScreenController） | どの画面を表示するかを決め、後方映像などの優先表示と元画面への復帰を管理する |
| 他ソフトとの通信（ServiceBridge） | 画面操作を止めずに指示を送り、状態・映像・結果を受け取る。返事の待ち時間に上限を設ける |
| 画面用データ管理（AppState） | 表示画面、車速、録画状態などを保持し、変更があった部分を画面へ伝える。各サービスについて`transport_status`、`service_status`、データの`validity`を個別に保持する。Android位置情報は`provider_status`、OsmAnd画面は`display_status`として管理し、GPS測位中・信号喪失・補正中も区別する。OBD2各値の`valid_for_ms`を保持し、100ms周期で期限切れを監視して古い値を`—`表示へ戻す |
| 画面表示（QML各画面） | 情報を表示し、タッチ操作を受け付ける。カメラやGPIOを直接操作しない |

以下はPython + PySide6/QMLを使う場合の設計案であり、記載したUIモジュールやファイルはまだ作成していない。
UI内部は原則として1つのアプリの中で役割を分ける。録画や位置補正は、これまでの設計どおりUIとは別のソフトとして動かす。
図の実線矢印は操作・データの流れ、点線矢印は「起動時に準備して組み合わせる関係」を示す。

#### 本書での言葉の使い方

本文と図は動作が分かる日本語を基本とし、プログラム上の名前は対応が分かるように併記する。

| 表現 | この設計書での意味 |
| --- | --- |
| 機能 | UIが利用者に提供する動作。例：音楽の再生状態を表示する |
| モジュール | 機能を実現するために役割ごとに分けたソフトウェアの構成要素。例：ServiceBridge、AppState |
| 関数 | モジュール内で特定の処理を行う単位。例：on_service_event、apply_update |
| 担当ソフト（サービス） | 録画・音楽再生などを担当し、UIとは別に動くソフト |
| 更新通知の受信開始・終了 | 車速などが変わったときに情報を送ってもらう登録・解除。解除しても送信元のソフトは終了しない |
| 映像の受信開始・終了 | 表示に使うカメラ映像を受け取り始める・やめること。録画の開始・停止とは別 |
| 画面操作を担当する処理（主スレッド） | タッチ操作や画面用データの更新を行う処理。長い通信待ちをここで行うと画面が反応しなくなる |
| 裏で動く処理 | 画面操作とは分けて動かす通信・設定保存などの処理。終了時には通信を閉じるなどの後片付けが必要 |
| 使用終了の連絡 | 表示側が画像データを使い終わったと伝えること。他の処理も使用中なら、そのデータをまだ削除・再利用しない |

| 実線の矢印 | 動作中の操作・状態・処理結果の受渡し。矢印の先が受取側 |

| 破線の矢印 | main_appによる準備・終了の管理。枠内のモジュール全体が対象 |

番号は接続を識別するためのものであり、①～⑦を必ず順番に実行するという意味ではない。

**モジュール間で渡すもの**

| 接続 | 送る側 → 受け取る側 | 具体例 |
| --- | --- | --- |
| ① | QML画面群 → ScreenController | 「音楽画面を開く」「再生ボタンを押した」 |
| ② | ScreenController → ServiceBridge | 「音楽を再生するよう要求する」「後方映像を受け取り始める」 |
| ③ | ServiceBridge → ScreenController | 「音楽は再生中」「リバースがON」「要求した操作が失敗した」 |
| ④ | ScreenController → AppState | 現在の再生状態、表示する画面、警告などを更新する。判断に必要な現在値もAppStateから参照する |
| ⑤ | AppState → QML画面群 | 「再生状態が変わった」「後方映像を表示する状態になった」 |
| ⑥ | ServiceBridge → QML画面群 | 受信したカメラ映像をVideoSurfaceへ渡す |
| ⑦ | QML画面群 → ServiceBridge | 表示し終えた画像を、再利用できるか確認するために連絡する |

main_appは起動時に各モジュールを準備し、どの情報をどの関数へ渡すかを設定する。動作中の操作や状態通知が毎回main_appを通る構成にはしない。
QML画面群からServiceBridgeへ渡す⑦は画像の使用終了だけであり、画面選択・再生指示・映像の受信開始と終了はScreenControllerを通す。

⑥・⑦の経路には、ServiceBridge側のFrameChannelと表示補助部品frame_presenterが含まれる。これらは主要モジュール間の受渡しを補助する内部部品であり、詳細は[3.5.3](#dd-34)、[3.5.5](#dd-36)、[図4-4](#dd-interface-diagrams)に記載する。
外部アプリの実画面は、現行実装ではSway Waylandセッション上のWaydroid外部ウィンドウとして扱い、固定したナビ表示領域へ移動・リサイズする。Wayland外部サーフェスのQML領域への完全埋込みは将来検討とし、現行実装の前提にはしない。QML側には地図風のデモ画面や、外部画面の下に隠れる検索・ズーム・案内カードなどの操作部品を配置せず、OsmAndの表示状態を外部サービスの結果として管理する。外部画面が起動するまでの領域には、起動待ち状態だけを表示する。

| 境界 | 設計規則 |
| --- | --- |
| QML → Python | 操作の意図を通知する。QMLからGPIO・データベース・他ソフトを直接操作しない |
| 状態の更新 | ScreenController経由でAppStateを更新し、画面からの直接書換えを禁止する |
| UIとは別に動くソフト | ServiceBridgeに通信を集約する。相手ソフトが勝手に表示画面を切り替えない |
| 映像 | 容量の大きい画像データはAppStateへ入れず、3.5.3・3.5.5の表示専用経路を使う |
| main_app | 必要なモジュールの準備と終了管理に限定し、画面ごとの操作判断はScreenControllerに任せる |

<a id="dd-feature-connections"></a>
### 3.2 機能別処理フローチャート

[2.1](#dd-functions)の各機能について、開始から条件判断、処理、完了までの流れを示す。各処理には担当モジュールを併記する。複数のモジュールが協力する処理では、担当欄の矢印で情報の受渡し順を示す。

| 図の記号 | 意味 |
| --- | --- |
| 丸みのある枠 | 処理の開始・終了 |
| 四角 | 実行する処理。担当欄はその処理を行うモジュール |
| ひし形 | 条件判断。「はい／いいえ」に従って進む |
| 矢印 | 次に行う処理。繰り返しの矢印は次の通知・操作・確認機会への継続 |

色は担当モジュールを区別し、複数担当の場合は先頭の担当に合わせる。モジュール間の接続関係全体は[3.1](#dd-31)、各関数の内部処理は[3.7](#dd-310)に記載する。
AppStateとQMLだけを示す表示更新の処理でも、表示データへの書込みはScreenControllerが行う。QMLや通信処理からAppStateを直接書き換えない。

担当ソフトの応答・映像を待つ箇所でも画面操作は止めず、別の操作やリバース通知を処理する。結果が届くか期限切れになった時点で、その要求に対応する処理を再開する。起動・表示・設定要求は現在の要求番号と照合し、古い結果で新しい表示を上書きしない。
映像を表示する処理はAppStateを通さず、ServiceBridgeの画像管理とframe_presenterを介してVideoSurfaceへ渡す。画像の使用終了の連絡と使用中の画像を解放しない規則は、全ての映像表示で適用する。

### 3.4 モジュール間の処理順序

以下はナビ起動中にリバースがONになる場合の例。UIとは別に動くソフトの準備完了と前面表示の許可を分ける。

```mermaid
sequenceDiagram
    participant Q as QML画面
    participant C as 画面切替管理
    participant S as 画面用データ管理
    participant B as 他ソフトとの通信
    participant N as ナビ管理担当ソフト
    Q->>C: ナビ選択
    C->>S: 選択画面と画面要求の通し番号を更新
    C->>B: ナビ起動要求
    B->>N: 起動を依頼
    B->>C: 有効なリバースON通知
    C->>S: 復帰先保存・後方優先へ変更
    S-->>Q: 後方優先の表示通知
    C->>B: 表示用の後方映像の受信を依頼
    N-->>B: 起動完了
    B-->>C: 操作結果・準備状態
    C->>S: ナビ準備済みだけを反映
    Note over C,Q: 後方優先中はナビを手前に表示しない
```

| 処理の分担 | 行う仕事 | 他の処理への渡し方 |
| --- | --- | --- |
| 画面操作を担当する処理 | タッチ操作の受付、表示画面の判定、画面用データの更新 | 短時間で終え、長い通信待ち・ファイル読書きを行わない |
| 裏で動く通信処理 | 接続、送受信、内容確認、再接続 | 確認済みの通知を一時的に保存し、画面操作を担当する処理へ順に渡す |
| 裏で動く設定保存処理 | 設定ファイルへの書込みと結果通知 | どの設定変更の結果かを識別できる番号を付けて返す |
| 映像受渡し・描画 | 圧縮映像を画像へ戻す処理、形式の変換、表示 | 採用する表示方式で決められた実行場所を守り、画像の使用開始・終了を管理する |

終了時は新しい操作を受け付けず、状態通知と映像の受信を終了する。表示中の画像を使い終えたことを伝え、通信を閉じて裏で動く処理を終了する。
遅れて届いた通知は、「終了処理中か」「どの受信開始に対応する通知か」を確認し、閉じた画面には渡さない。
通信処理の終了や設定保存には待ち時間の上限を設け、いつまでも終了できない状態を避ける。時間内に終わらなければ、正常終了・保存成功とは記録しない。

### 3.5 モジュール詳細

カーナビUIを構成する5つのモジュールについて、内部の処理・入出力・役割分担を説明する。各モジュールの説明を3.5.1～3.5.5に記載する。モジュール間の処理順序は[3.4](#dd-38)、ファイル構成は[3.6](#dd-37)を参照する。

<a id="dd-32"></a>
#### 3.5.1 起動・終了管理（main_app）の内部構成

```mermaid
flowchart LR
    Config["設定読込・検証"] --> Create["画面アプリと<br/>必要なモジュールを準備"]
    Create --> Wire["情報が届いたときに<br/>動く関数を設定"]
    Wire --> Load["QML読込・初期状態表示"]
    Load --> Run["操作・通知を待って処理"]
    Run --> Stop["受信終了・保存・後片付け"]
```

| 公開関数の案 | 入力・出力 | 役割（処理手順は3.7参照） |
| --- | --- | --- |
| load_ui_config | 設定ファイル → 検証済み設定 | バージョン・型・範囲を確認。秘密情報は画面へ渡さない |
| build_dependencies | 設定 → 準備したモジュールの一覧 | AppState、ServiceBridge、ScreenControllerの順に生成する |
| connect_components | 準備したモジュールの一覧 → 設定結果 | 状態や操作結果が届いたとき、どの関数に渡すかを設定する。設定保存や通信終了の結果を受け取る処理も指定する。QMLのボタン操作との対応付けはload_viewで行う |
| load_view | 画面全体の定義と操作・データの受渡し先 | QMLには表示用AppStateと操作用Controllerだけを公開する |
| begin_shutdown | 停止理由 → 終了結果 | 新しい操作を受け付けず、状態・映像の受信を終了し、設定を保存して裏で動く処理を終了する。終了待ちには上限を設ける |

設定ファイルの読み書きなど、完了まで待ち時間が発生する処理で画面操作を長時間止めない。
画面全体の読込失敗など、UI自体を表示できない異常は理由をログに残して起動失敗として終了する。
UIとは別に動くソフトが未起動という理由だけではUI起動を失敗させない。UIの再起動で録画・位置補正担当ソフトを再起動しない。

<a id="dd-33"></a>
#### 3.5.2 画面切替管理（ScreenController）の内部構成

下図の各要素は、画面切替管理の中で行う仕事を分けたものとする。最初から全てを別のプログラム部品にせず、個別試験や他の場所での利用が必要になった段階で分ける。

```mermaid
flowchart TB
    User["QMLからの操作"] --> Check["操作受付・入力検証"]
    Notify["通信結果の受信・期限確認"] --> Merge["担当ソフトの状態の更新"]
    Check --> Gate["操作許可判定"]
    Merge --> Decide["表示優先順位の再評価"]
    Gate --> Decide
    Decide --> Route["画面切替・元画面の記憶"]
    Route --> Commit["画面用データを更新"]
    Route --> Command["必要な指示を通信処理へ渡す"]
```

| 公開関数の案 | 役割 | 主な判定・結果（処理手順は3.7参照） |
| --- | --- | --- |
| request_screen | 画面選択を受理 | 画面ID、操作許可、後方優先を検査する |
| handle_action | 再生・音量・設定等の受付 | 部品ID・操作に必要な値・許可範囲を検証し、拒否理由を返す |
| on_service_event | 通信処理から受けた通知の反映 | 担当ソフトの状態・観測期限を更新する |
| reevaluate_display | 最優先の画面を決定 | 後方優先、俯瞰許可、通常選択の順に判定する |
| restore_previous_screen | 割込みからの復帰 | 復帰先の利用可否を再評価し、利用不可ならホームへ |
| on_command_result | 後から届く処理結果の確認 | 操作の識別番号（command_id）と、画面要求の通し番号を照合する |
| expire_stale_data | データの期限確認 | 古い車速やリバースをUNKNOWN等へ更新し、操作許可を取り消す |

画面切替では「ソフトを起動する依頼」と「そのソフトを手前に表示する依頼」を分ける。起動完了後にも優先順位を再評価する。
リバースONの初回だけprevious_screenを保存し、定期ON通知や担当ソフトへの再接続で復帰先を上書きしない。
「表示してよいかを判断する処理」と「実際に他ソフトへ指示を送る処理」を分け、それぞれ試験できるようにする。
画面用データの変更通知を、同じ変更を指示する処理へそのまま戻さない。通知と更新が際限なく繰り返されることを防ぐ。

<a id="dd-34"></a>
#### 3.5.3 他ソフトとの通信（ServiceBridge）の内部構成

```mermaid
flowchart TB
    C["画面切替管理"] --> Send["操作内容と識別番号を確認"]
    Send --> Adapter["相手ソフトごとの通信手順"]
    Adapter --> Worker["裏で通信を行う処理"]
    Worker --> External["UIとは別に動くソフト"]
    External --> Worker
    Worker --> Validate["バージョン・送信元・順序・形式検証"]
    Validate --> Result["現在の状態・操作の結果"]
    Result --> C
    Validate --> Frame["画像データの受渡し<br/>使用開始・終了を管理"]
    Frame --> Surface["QML側の映像表示窓口"]
```

| 内部要素 | 役割 | 制約 |
| --- | --- | --- |
| 操作依頼の管理（CommandRegistry） | 操作の識別番号、画面要求の通し番号、待ち時間の上限、結果を管理 | 受付と完了を分け、古い結果を新要求へ適用しない |
| 相手別の通信手順（ServiceAdapters） | 相手ソフトごとに違う指示・通知の形式を、UIで使う共通形式へ変換 | 相手ソフトごとの操作手順や通信方式を、QML側で扱わない |
| 裏で動く通信処理（TransportWorker） | 接続、送受信、再接続 | 通信を並行して行う処理の数は実装時に決める。相手ソフトの数だけ増やす必要はない |
| 受信内容の確認（EventValidator） | 共通仕様で決めた送信元・番号・値・順序を確認。`schema_version=1`だけを受け入れ、`boot_id`と`sequence`で古い通知を破棄 | 古い測定値を受け取り直しても、利用できる期限を延ばさない |
| 継続して受け取る情報の管理（SubscriptionRegistry） | 状態通知・映像の受信開始と終了を管理 | 画面を切り替えた後は、もう使わない通知・映像を受け取り続けない。録画自体は停止しない |
| 画像の受渡し（FrameChannel） | 表示する画像データと、その保存場所を表示部品へ渡す | 表示待ち画像の数に上限を設け、最新の画像を優先する。使用中の画像を勝手に削除・再利用しない |

呼出し口の名前は、操作指示の送信（send_command）、状態通知の受信開始（subscribe_state）、映像の受信開始（subscribe_video）、指定した受信の終了（unsubscribe）、通信全体の終了（close）とする。02 Waydroidナビ管理との実通信は、Pi 5上のUnixドメインソケットを通るJSON Linesで行う。09 OBD2車両情報取得と03 現在地補正も、それぞれ別のUnixドメインソケットを使用し、OBD2やGPSの周期通知がナビ操作を遅延させないようにする。03からは`position.status`、`position.update`、`position.invalidate`を受け取り、GPS測位中・信号喪失・補正中を画面状態へ反映する。1行1JSONオブジェクトとして要求・応答を交換し、状態変化は`event`付きの通知として受け取る。
受け取った状態通知（service_event）と操作結果（command_result）は、画面操作を担当する処理へ渡す。ServiceBridgeの通信処理はUIスレッドを待たせないように別スレッドで実行し、QtのSignal/Slotで画面操作側へ通知する。02 Waydroidナビ管理は要求受付時に`accepted=true`と`QUEUED`を返し、処理完了時に同じ`command_id`の`command_result`を通知する。Windows開発環境でソケットがない場合は未接続状態を通知し、画面単体の確認を妨げない。
表示待ちの状態情報は、相手ソフトと項目ごとに最新値を残す。一方、操作結果は操作の識別番号ごとに成功・失敗などの最終結果を保持し、別操作の結果で上書きしない。
再接続後は相手ソフトに現在の状態をまとめて送り直してもらう。接続が切れる前の操作を勝手にやり直さない。

圧縮映像を画像へ戻したり、表示用の画像形式へ変換したりする場合も、重い計算でタッチ操作を止めない。
画像の保存場所を伝える形式、ソフト間の受渡し方法、表示側が使い終わったと知らせる時点は、06 カメラ表示・録画の設計と合わせて決める。画像を複製せずに受け渡せるかは、まだ確認できていない。

<a id="dd-35"></a>
#### 3.5.4 画面用データ管理（AppState）の内部構成

AppStateは、画面に見せる情報をまとめて置いておく場所である。例えば「車速42 km/h」「音楽は再生中」「今は後方画面」という情報を保持する。
データベースや録画保存先ではなく、主にアプリが動いている間のメモリ上で管理する。

| 役割 | 具体例 |
| --- | --- |
| 値を保持する | 現在の車速と、その値がいつ測られたかを保持する |
| 状態も一緒に保持する | 同じ数値0でも「停止中」と「取得できなかった」を区別する |
| 変わった部分を伝える | 再生状態が変わったら、音楽画面の表示更新を知らせる |
| 複数画面で情報を揃える | 共通バーと音楽画面で、同じ再生状態・音量を使う |
| 表示用の形で返す | 内部の車速をkm/hへ換算し、単位とともに画面へ渡す |
| OBD2の取得量を切り替える | 車両情報画面では詳細項目、それ以外では車速・冷却水温など最小項目だけを取得するようServiceBridgeへ要求する |

「どの画面へ切り替えるか」を決めるのはScreenController、ボタンの配置や色を決めるのはQMLである。
AppStateはその判断に従って値を保持・通知するが、車両への通信、録画、画面切替の判断そのものは行わない。

```mermaid
flowchart TB
    C["画面切替管理<br/>画面操作側から更新"] --> State["画面用データ管理<br/>更新をまとめる"]
    State --> Display["画面状態<br/>選択・実表示・復帰先"]
    State --> Services["担当ソフトの状態<br/>値・品質・期限・接続"]
    State --> Commands["操作状態<br/>処理中・結果・拒否理由"]
    State --> Settings["設定状態<br/>確定値・編集中"]
    State --> Warnings["警告一覧<br/>発生・確認・回復"]
    Display --> Notify["変更した項目だけ通知"]
```

| 状態グループ | 内容 | 更新規則 |
| --- | --- | --- |
| 表示画面の情報（DisplayState） | selected_screen、effective_screen、camera_mode、previous_screen、request_generation | 切り替える画面を決めてから、関係する値をまとめて更新する |
| 担当ソフトの情報（ServiceState） | service_health、reverse_validity、motion_state、項目別観測値・期限 | 真の0、未取得、期限切れを区別する |
| 操作の処理状況（CommandState） | pending_commands、操作結果、拒否理由 | 成功・失敗などの最終結果が出た操作は、保存期間を過ぎたら一覧から整理する |
| 設定値（SettingsState） | user_settings、editing_settings | 担当ソフトから届いた適用結果を確認してから確定値へ反映 |
| 警告一覧（WarningModel） | 発生元・コード・重要度・確認状態 | 原因状態と「利用者が確認した」を別に持つ |

AppStateを書き換えるのは、画面操作を担当する処理だけとする。裏で動く通信処理などは結果を通知し、画面のデータや表示部品を直接書き換えない。
画面には表示用の値や一覧を渡し、画面側から元データを書き換えられないようにする。変更があった項目・行・画面だけを更新し、同じ値の通知を繰り返さない。
画像データそのもの、秘密情報、容量の大きな録画ファイル一覧は保持しない。画面に表示する単位や桁数の変換では元データを書き換えず、操作許可の判断に使う数値を丸めない。
詳しいデータ項目は[5.2 UI状態・設定の管理](#dd-52)と対応させる。

`FeatureController.completed`はQtスレッドへ結果を戻すための通知。QMLコンテキスト名は`uiFeatures`。音楽・追加設定・警告の状態はこのオブジェクトが保持し、既存AppStateへ同じ値を重複保持しない。上記以外の関数フローには将来構成の論理名も含まれる。

公式音楽サービスの画面管理は`uiFeatures.webMusic`（`OfficialMusicController`）で公開する。音楽画面には保存済み音楽・YouTube Music・Spotifyの切替を設ける。保存済み音楽のMopidy操作と、公式Web画面の起動・終了を混同しない。公式画面選択時はMopidyの再生・音量・プレイリスト部品を隠し、Linux/Sway上の専用Chromiumを中央領域へ配置する。有効な走行車速がある場合は公式画面を表示しない。OBD2車速が未取得・失効の場合は警告付きの代替モードで表示できる。別画面では専用の非表示ワークスペースへ移動してブラウザとページ状態を保持し、音源切替とUI終了では専用ブラウザを閉じる。通信・認証の詳細は[12 オーディオ連携 4.0.1](12_オーディオ連携.md#dd-official-music)を参照する。

操作許可はOBD2の`VALID`・有限数`value=0`・単位`m/s`または`km/h`・有限の正の`valid_for_ms`から判定する。許可期限は通知の残り期限と5秒の短い方。期限切れ監視は100ms周期で、操作受付時はその場の単調時刻でも再判定する。有効な走行車速を受信した場合は設定変更・復元、録画設定、送信一時停止/再開、プレイリスト編集、録画再生を許可しない。OBD2車速が未取得・未接続・車速値失効の場合は`AppState.obdUnavailable`による代替モードとして警告付きで許可する。車速0の停車確認期限だけが切れた場合は、車速が有効なら操作を許可しない。新しい走行通知で再生を停止し、遅れたコピー完了も破棄する。受付済みの保存・送信操作の取消や実車安全保証はしない。

停車確認では、同じOSで動作するOBD2サービスの`acquired_mono`と`time_quality=monotonic`を必須とする。許可期限は`acquired_mono + min(valid_for_ms, 5000) / 1000`であり、受信時刻を起点にしない。未来・未記載・既に失効した取得時刻は操作許可に使わない。

履歴の保存先は設定ファイルと同じ場所の`<設定ファイル名の拡張子を除いた部分>.warnings.json`。同じ設定先のUIを起動中の全期間ロックする。設定保存は別ロックと読込時のバイト列照合で競合を検出する。運用はローカルディスク上とし、ロック非対応の外部エディタ等との完全な排他は保証しない。具体的な設定と制約は[付録9](../付録9_UI追加機能導入手順.md)を参照。

### 3.7 関数のフローチャート

各関数について、所属モジュール、入力、返す結果、処理手順を記載する。関数名・入出力は実装前の設計案であり、既存ソースに追加済みの関数ではない。

<a id="dd-310-3"></a>
#### 3.7.3 connect_components（情報が届いたときに動く関数を設定する）

この関数は、「どんな情報が届いたら、どの関数に渡すか」をUIの起動時に設定する。
ここでいう「接続」は配線やネットワークへの接続ではなく、プログラム内で情報を渡す相手を指定することを意味する。

例えば、音楽担当ソフトから「再生中」という情報が届いたら、通信を担当するServiceBridgeがその情報を受け取り、画面切替管理の`on_service_event`へ渡す。その後、表示用データが更新され、画面に再生状態が表示される。
`connect_components`は、この「情報が届いたら関数へ渡す」という動きを先に設定するだけで、この時点で音楽を再生したり、受信処理の関数を実行したりするわけではない。

| 届いた情報 | その情報を渡す関数・処理 | 受け取った後に行うこと |
| --- | --- | --- |
| ServiceBridgeが受け取った車速・再生状態など | ScreenControllerの`on_service_event` | 情報が有効かを確認し、表示用データや表示画面を更新する |
| ServiceBridgeが受け取った操作の成功・失敗など | ScreenControllerの`on_command_result` | どの操作の結果かを確認し、処理状況を更新する |
| 設定ファイルの保存結果 | 保存を依頼した側の結果確認処理 | 保存できたかを確認し、失敗した場合は理由を記録・表示する |
| 通信処理の終了結果 | main_appの終了状況を確認する処理 | 後片付けが完了したかを確認する |

設定保存・終了結果を受け取る関数の具体名は、実装時に確定する。

| 項目 | 内容 |
| --- | --- |
| 入力 | 準備済みのServiceBridge・ScreenControllerなどと、結果を受け取る関数 |
| 返すもの・通知するもの | 情報の渡し先を設定できたか。失敗した場合はその理由 |

```mermaid
flowchart TB
    A["情報の種類と渡し先を確認"] --> B{"必要な渡し先をすべて設定済みか"}
    B -->|"はい"| C["設定完了を返す"]
    B -->|"いいえ"| D["状態が届いたら<br/>on_service_eventへ渡すよう設定"]
    D --> E["操作結果が届いたら<br/>on_command_resultへ渡すよう設定"]
    E --> F["保存結果と通信終了の結果も<br/>それぞれの確認処理へ渡すよう設定"]
    F --> G{"必要な渡し先をすべて設定できたか"}
    G -->|"はい"| H["設定した組合せを記録"]
    H --> C
    G -->|"いいえ"| I["今回追加した設定だけ取り消し<br/>失敗理由を返す"]
```

一部の渡し先が設定済みなら、未設定のものだけ追加する。同じ情報を同じ関数へ2回渡す設定にしない。
この段階ではPython側のモジュール間だけを設定する。QMLの画面はまだ準備できていないため、ボタン操作や画面表示との対応付けは`load_view`で行う。

### インターフェース図

インターフェースとは、モジュール同士、またはUIと担当ソフトが操作や情報を受け渡す接点を指す。以下では、UI内部の接点と、UIの外で動く担当ソフトとの接点を分けて示す。
矢印は情報を渡す方向、矢印上の文字は渡す内容を表す。青はUI内部、緑は担当ソフト、灰色の破線は将来対応を示す。ソフト名の先頭番号は、[詳細設計一覧](README.md)の文書番号と対応する。
本図は論理的な接続の設計案であり、実装済みのAPIを示すものではない。Pi 5内のソフト間通信方式、Ethernet上の通信方式、ポート番号は[共通仕様](00_共通仕様.md)に従って別途確定する。

#### 図4-1 利用者操作とUI内部の接点

```mermaid
flowchart LR
    User["利用者"] -->|"タッチ操作"| View["画面表示<br/>QML"]
    subgraph UI["カーナビUI内部"]
        View -->|"IF-01 操作名・指定値"| Controller["画面切替管理<br/>ScreenController"]
        Controller -->|"IF-02 操作指示・受信依頼"| Bridge["他ソフトとの通信<br/>ServiceBridge"]
        Bridge -->|"IF-03 状態・処理結果"| Controller
        Controller -->|"IF-04 表示値の更新"| State["画面用データ管理<br/>AppState"]
        State -->|"IF-05 表示値・変更通知"| View
    end
    classDef ui fill:#E8F1FC,stroke:#376996,color:#172B40;
    class View,Controller,Bridge,State ui;
```

| 接点 | 主な受渡し内容 | 対応する関数・規則 |
| --- | --- | --- |
| IF-01 | 画面ID、操作部品ID、音量などの指定値 | `request_screen` / `handle_action`。QMLからGPIOや外部ソフトを直接操作しない |
| IF-02 | 操作名・引数、状態または映像の受信開始・終了 | `send_command` / `subscribe_state` / `subscribe_video` / `unsubscribe` |
| IF-03 | 検証済み状態、操作の識別番号と結果・理由 | `on_service_event` / `on_command_result`。表示変更の可否はControllerが判断する |
| IF-04 | 更新する項目・値・測定時刻・有効性 | `apply_update`。関係する値をまとめて更新する |
| IF-05 | 表示画面、表示用の値・単位・警告、変更した項目 | `get_display_data`と変更通知。QMLから元データは書き換えない |

矢印は通知・呼出しの接点を示し、外部の処理が完了するまで待ち続けることを意味しない。容量の大きい映像はこの図のAppState経由ではなく、図4-4の専用経路で表示する。

操作要求には`command_id`、操作名、引数、有効期限を付ける。返信は同じ`command_id`と対応させ、「受理」「実行中」「成功」「拒否」「失敗」を区別する。返事が届かなければ「結果未確認」とし、成功扱いや無条件の再送はしない。
OsmAnd・LIVIの実画面はナビ表示領域へ配置する対象として扱う。起動完了と手前への表示は別の操作であり、表示直前にもリバースなどの優先条件を確認する。現行実装ではSwayの外部ウィンドウを同じ表示領域へ移動・リサイズする。Wayland外部サーフェスの完全埋込みは将来検討とし、具体的な画面切替手段は[4.5](#dd-45)で検証する。

#### 図4-3 車両・運用状態の受信

```mermaid
flowchart LR
    Vehicle["09 OBD2車両情報取得"] -->|"専用ソケット: vehicle.update / invalidate / status"| Bridge["カーナビUI<br/>ServiceBridge"]
    Rear["15 サブコントローラ1後方系<br/>別筐体: Pi 3B"] -->|"Ethernet: リバース状態・入力品質"| Bridge
    Fan["10 冷却ファン制御"] -->|"CPU温度・回転状態・警告"| Bridge
    Upload["07 Google Driveアップロード・削除"] -->|"送信状態・失敗理由"| Bridge
    Bridge -->|"送信元・順序・期限を確認した状態"| Controller["ScreenController<br/>表示・操作許可を判断"]
    classDef ui fill:#E8F1FC,stroke:#376996,color:#172B40;
    classDef service fill:#EAF5EC,stroke:#4A7753,color:#203A26;
    class Bridge,Controller ui;
    class Vehicle,Rear,Fan,Upload service;
```

状態通知には、値だけでなく送信元・起動ID・連番・測定時刻・有効期間・有効性・理由を付ける。取得失敗や期限切れを数値0やリバースOFFに置き換えない。通信遅延を含めた期限の判定は共通仕様に従う。
OBD2の取得モードは、UIが車両情報画面を表示している間だけ`full`とする。それ以外は`minimal`とし、車速など常時必要な項目だけを取得する。画面切替時の`set_polling_mode`はServiceBridgeからOBD2専用ソケットへ送る。QMLはOBD2機器へ直接接続しない。
アプリの準備状態は図4-2、カメラ・録画状態は図4-4で示す。位置品質は03 現在地補正から専用ソケットで直接通知する。上部GPS欄と車両情報画面は、同じ`GpsStatus`の判定結果を表示する。

| GPS欄の表示 | 判定条件 | 表示色 |
| --- | --- | --- |
| サービス未接続 | 03のソケットに未接続、または切断済み | 警告色 |
| 確認中 | ソケット接続直後で、有効な状態通知をまだ受信していない | 警告色 |
| 測位待ち | 有効な初回測位をまだ取得していない | 警告色 |
| 測位中 | 品質確認済みのGPS位置が表示期限内 | 正常色 |
| 補正中 | 品質確認済みのセンサー推定位置が表示期限内 | アクセント色 |
| 信号喪失 | 過去に有効な位置を取得したが、03が現在位置を利用不可と通知 | 警告色 |
| 更新停止 | 位置表示期限切れ、状態通知が5秒途絶えた、または通知の時刻・品質・期限を確認できない | 警告色 |

ソケット接続はUSB GPS受信機の接続を証明しない。USB接続状態、衛星数、OsmAndへの登録成功は本表示の判定対象外とする。GPS単独運用では信号喪失中に補正中を表示しない。車両情報画面には`gpsDetail`として状態理由を2行以内で表示する。

`ScreenController`は`schema_version=1`、空でない`boot_id`、正の整数`sequence`を検査する。位置通知はナビ・OBD2と独立した連番で管理し、重複、順序逆転、廃止済み起動IDを拒否する。接続通知は測位状態を「確認中」に戻し、切断時には有効な測位・補正表示を直ちに解除する。

`AppState`は`GpsStatus`を100ms周期で監視する。03は状態を1秒周期で配信し、UIは状態の送信時刻から5秒を通知期限とする。位置表示期限は`position.update.display_valid_for_ms`（未指定時は`valid_for_ms`）、状態照会では`position.status.position_valid_for_ms`を使う。いずれも送信時点の残り時間で、同一Pi 5上の`issued_monotonic`との差から配送・Qtイベント待ち時間を引く。測定年齢`age_ms_at_send`は二重に引かない。期限切れでもソケットが開いている場合は、未接続ではなく「更新停止」とする。状態照会・定期通知で位置の元の期限を延長しない。

実装は`ui/state/gps_status.py`、`ui/state/app_state.py`、`ui/controllers/event_ordering.py`、`ui/controllers/service_bridge.py`。回帰試験は`tests/positioning/test_gps_display.py`で、切断、再接続、無通知、GPS単独喪失、補正失効、復帰、起動ID変更、順序検査を確認する。
UIはバックギア用GPIO、OBD2機器、ファンを直接読み書きしない。サブコン1からのリバース通知は、後方映像の受信経路とは独立して扱う。

| 受渡し内容 | 含める情報・管理方針 |
| --- | --- |
| 受信依頼 | 映像の方向・種別、受信登録ID、表示要求の通し番号。受信終了は自分の登録だけに適用する |

画面を閉じるときは表示用映像の受信を終了するだけで、06 カメラ表示・録画の録画や07 Google Driveアップロード・削除のアップロードを停止しない。UIは録画ファイルを直接削除せず、アップロード完了の確認と削除は07 Google Driveアップロード・削除が担当する。

### 4.1 画面一覧

カーナビUIが管理する画面を以下に示す。画面IDは設計・実装・試験で共通に使用し、表示名や配置を変更しても原則として変更しない。
本一覧は実装前の設計案である。画面ごとの配置・操作部品・切替条件は本書の4.2以降に記載し、実機条件に依存する数値や未検証の方式は未確定として管理する。

| 画面ID | 画面名 | 目的・主な表示内容 | 表示条件・入口 | 表示方式 |
| --- | --- | --- | --- | --- |
| UI-BOOT | 起動状態 | UI初期化の進捗、各担当ソフトの準備状態 | UI起動時。ナビの準備完了を待たずホームへ移行する | 自作画面 |
| UI-HOME | ホーム | 各機能への入口、時計、録画・接続などの状態概要 | UI初期化後、ホーム操作、通常画面への復帰先が利用できない場合 | 自作画面 |
| UI-NAV | ナビゲーション | OsmAndの地図、目的地、経路案内 | ナビ選択時。起動前は準備状態を表示し、未測位でも地図閲覧を可能にする | 外部アプリ画面へ切替 |
| UI-AA | Android Auto | LIVIを介したスマートフォン機能 | Android Auto選択時。接続前は未接続・準備状態を表示する | 外部アプリ画面へ切替 |
| UI-ANDROID | Waydroid | Waydroidホームから任意の導入済みAndroidアプリを選択する | ホーム画面中央下の「Waydroid」選択時 | Waydroidホームの外部ウィンドウへ切替 |

| UI-REAR | バックカメラ | 後方映像、映像未取得・遅延の警告 | 有効なリバースON通知で優先表示。有効なOFF通知で復帰を判定する | 自作画面。カメラ画面の後方優先モード |
| UI-SURROUND | サラウンドビュー | 前後左右の俯瞰合成、各領域の有効性 | 停止・駐車条件と合成担当ソフトの利用許可がある場合のみ。段階開発対象 | 自作画面 |
| UI-AUDIO | 音楽 | 曲情報、再生状態、選曲・再生・音量操作 | 音楽選択時。プレイヤー未接続時は操作を制限して状態を表示する | 自作QML操作画面 |
| UI-VEHICLE | 車両情報 | OBD2車速・回転数・水温・電圧、通信状態 | 車両情報選択時。未対応・未取得・期限切れを区別する | 自作画面 |
| UI-SETTINGS | 設定 | 表示・音量・接続などの利用者設定 | 設定選択時。初期案では停車確認時のみ変更可能とし、項目別制限は未確定 | 自作画面 |
| UI-RECORDINGS | 録画一覧（`recordings`） | 日付・方向検索、確定済みローカル動画の再生 | カメラ画面または設定から開く | 自作画面、QtMultimedia |

| UI-WARNINGS | 警告一覧（`warnings`） | 発生・確認・回復・前回起動時の履歴 | 上部バー・設定・車両情報から開く | 自作画面。最大100件をJSON保存 |

#### 一覧の適用ルール

- UI-REARは専用の画面IDを持つが、実装ではUI-CAMERAの表示部品を共用し、映像取得処理を二重に起動しない。
- 警告は後方映像全体を不必要に隠さない。リバース中のナビ・Android Autoの準備完了で後方表示を奪わない。
- 外部アプリの起動前・未接続時の案内は自作UIが表示する。ナビ画面の主表示領域をOsmAnd、LIVIまたはWaydroidホームの表示領域として予約し、現行実装ではSwayの外部ウィンドウをその領域へ移動・リサイズする。Wayland外部サーフェスの完全埋込みは将来検討とし、自作UIへの復帰方法を`WindowAdapter`で管理する。
- 担当ソフトが未準備・利用不可の場合は、その理由を表示する。古い映像・値を正常状態として表示し続けない。
- UI-WARNINGは常時表示する独立ページではなく、現在の画面へ重ねる共通要素とする。詳細確認画面の要否は未確定。
- ドアロックはセカンド開発のため初期画面の操作対象に含めない。BLE TPMSも未確定とし、採用時に車両情報画面への追加を検討する。
- 録画ファイル一覧は実装済み。再生は有効な車速0通知による停車確認時、または車速そのものを取得できない代替モードで警告付きで許可し、走行開始・車速値失効で停止する。停車確認期限だけが切れた場合は再生を許可しない。

### 4.2 画面レイアウト設計

横向きディスプレイを初期案とし、以下の領域で構成する。実際の向き・解像度・表示倍率が未確定のため、座標や寸法は確定値にしない。

| 領域 | 配置案 | 内容・制約 |
| --- | --- | --- |
| 状態表示領域 | 上部の細い帯 | 時計、録画、位置品質、接続状態を小さなアイコンと必要な文字で整理する。読める大きさを確保し、状態変化で配置を動かさない |
| 主表示領域 | 中央を広く確保 | 地図・カメラ・音楽など、選んだ機能を主役にする。不要な飾り枠を付けず、映像の縦横比と重要領域を守る |
| 共通操作領域 | 下部の固定位置 | ホーム、ナビ、音楽、カメラ、その他機能、音量などをアイコン中心に配置する案。操作の大きさを確保できない場合は項目数を減らす |
| 警告領域 | 主表示に重ねる固定位置 | 重要度と文字で状態を示す。カメラの主要な確認領域を避ける |

ホームは、6個の大きな色付きボタンを並べる案から、余白のある状態表示と下部の機能選択を中心にする案へ変更する。
中央の大きな機能ボタンには「ナビゲーション」「カメラ」「音楽」「車両情報」を配置する。ホームの「ナビゲーション」はOsmAndを選択して起動・表示する。中央下の「LIVI」はLIVIを選択して起動・表示し、「Waydroid」はWaydroidホームを表示する。Waydroidホームでは導入済みAndroidアプリを利用者が選択できる。画面最下部の共通「ナビ」は、直前にOsmAndとLIVIのどちらを表示したかを`navigationMode`で保持し、その対象を再表示する。Waydroidホームの表示ではこの選択を変更しない。下部に収まらない機能は「その他機能」から開く一覧へまとめる。
「その他機能」の一覧表示はUI-HOMEの表示部品として扱い、独立した新しい画面IDは追加しない。各機能の選択は既存のACT-OPENで扱う。戻る操作は必要な画面に表示する。
項目の順序・操作領域寸法は実機で確定する。サラウンドはカメラ画面から選択する。リバース優先時は通常画面へ離れる操作を制限し、後方映像を大きく表示する。

| 画面 | 主表示領域の構成案 |
| --- | --- |
| UI-BOOT | 担当ソフト別の準備状態。裏付けのない進捗率や残り時間は表示しない |
| UI-HOME | 4つの主要機能入口と状態概要。ナビゲーションはOsmAnd固定、中央下にLIVI直通とWaydroidホーム直通を配置する。画面最下部のナビは最後に選択したOsmAndまたはLIVIを再表示する |
| UI-NAV / UI-AA | 起動待ちは自作の状態画面、準備後は対象アプリのウィンドウへ切替 |
| UI-CAMERA | 選択中の映像を大きく表示し、カメラ名・状態・方向選択を添える |
| UI-REAR | 後方映像を最大限確保し、不要な選択操作を隠す。未校正の距離線は表示しない |
| UI-SURROUND | 車体周辺の合成映像と非観測領域を表示。距離の正確性を過信させる装飾を避ける |
| UI-AUDIO | 曲名・アーティスト、再生状態、再生/一時停止・前後曲・音量 |
| UI-VEHICLE | 車両値を単位付きで整理。ECU電圧とアダプタ端子電圧、車両水温とCPU温度を区別 |
| UI-SETTINGS | 表示・音声・接続に分類し、現在値、編集値、適用結果を区別 |
| UI-WARNING | 重要度、発生元、短い原因、操作可否。原因未解消で「正常」と表示しない |

外部アプリ表示中に自作の上部・下部領域や警告を重ねて表示できるとは仮定しない。Sway方式では自作UI、OsmAnd、LIVI、Waydroidホームが別ウィンドウのため、上部バーや下部ナビへのタッチで自作UIがフォーカスを取得すると、表示中の外部アプリが背面へ回る場合がある。OsmAnd、LIVIまたはWaydroidホームの表示中に上部バーを押した場合と、表示中のナビを下部ナビから再選択した場合は、画面切替やアプリ再起動を行わない。クリック処理が完了して自作UIの前面化が落ち着いた後、既定40msの単発タイマーで保存済みのSwayウィンドウIDへフォーカス要求を1回送る。保存IDが無効な場合だけ対象を再検出し、同じ固定領域へ再配置する。連続操作ではタイマーを再始動してフォーカス要求を一件にまとめる。
警告通知・ホーム復帰・リバース割込みの実現方式は[4.5 外部アプリ連携](#dd-45)で検証する。

<a id="dd-43"></a>
### 4.3 操作仕様・共通部品

以下の部品IDは設計上の識別子であり、実装クラス名ではない。1回の操作は押下位置と解放位置を確認して確定し、画面切替後に古い押下を新画面へ持ち越さない。

| 部品ID | 操作 | 処理 | 無効・待機時 |
| --- | --- | --- | --- |
| ACT-HOME | タップ | 通常画面からホームへ。画面を隠しても録画・音楽を停止しない | リバース優先中は画面離脱を禁止 |
| ACT-BACK | タップ | 現在の自作画面内の履歴を1段戻る。履歴なしはホームへ | 外部アプリ内の「戻る」とは別契約。リバース優先中は離脱禁止 |
| ACT-OPEN | 機能選択 | 利用条件を確認し、既存画面表示または起動要求 | 同じ機能の起動待ち中は重複起動しない |
| ACT-OSMAND | タップ | ホームのナビゲーションからナビ方式をOsmAndへ切り替え、02 Waydroidナビ管理へ起動・表示を要求する | 起動中の重複要求を抑制し、失敗理由を上部警告へ表示する |
| ACT-LIVI | タップ | ナビ方式をLIVIへ切り替え、11 LIVI連携へ起動・表示を要求する | 起動中の重複要求を抑制し、失敗理由を上部警告へ表示する |
| ACT-ANDROID | タップ | 「Waydroid」から02 Waydroidナビ管理へWaydroidホームの表示を要求し、Androidアプリ選択画面を固定領域へ配置する | Waydroid未準備・ホーム画面未検出時は自作画面に理由を表示する |
| ACT-PLAY | タップ | 確認済み再生状態に応じて再生または一時停止を要求 | 状態不明・通信断では無効。応答前に成功状態を確定しない |
| ACT-TRACK | 前曲/次曲 | 音楽担当ソフトへ1回の選曲要求 | 処理中は重複要求を抑制し、連打を無制限に蓄積しない |
| ACT-VOLUME | スライダー/段階調整 | 利用者指定音量を変更。連続入力は頻度制限し最新値を送る | 応答値と編集中の値を区別。低減中の実効音量とは分ける |
| ACT-CAMERA | 方向選択 | 表示用に受け取る映像の方向を切替 | リバース優先中は後方固定。未取得方向には理由を表示 |
| ACT-APPLY | 設定適用 | 型・範囲・操作許可を確認し、対象担当ソフトへ適用要求 | 完了までは適用中。失敗時に編集値を適用済みとして保存しない |
| ACT-CANCEL | 編集取消 | 未適用の編集値を破棄して確定値へ戻す | 担当ソフトへ送信済みの処理の取消可否は別途確認 |
| ACT-WARN-ACK | 警告確認 | 利用者が見たことを記録する | 原因状態は解除しない。未解消警告の表示方法は重要度別に定義 |

長押し、ダブルタップ、隠しジェスチャーは初期仕様では割り当てない。必要な機能は見える操作部品から実行できるようにする。
処理中の操作は識別番号（command_id）で管理し、待ち時間の上限を超えたら「結果未確認」とする。車体操作を含む要求を自動再送しない。

<a id="dd-44"></a>
### 4.4 共通表示・デザイン仕様

自作UIの方向性は「テスラのような、簡潔でモダンな車載画面」とする。具体的には、余白を活かした配置、少ない色数、主要情報の大きな表示、下部にまとめた操作を採用する。以下の色や配置は本システム用の設計案であり、テスラの仕様値ではない。

| 項目 | 設計方針 | 確定に必要な情報 |
| --- | --- | --- |
| 文字 | 本文、見出し、主要数値の役割別サイズを定義する。重要な状態を小さい注記だけにしない | 解像度、表示倍率、視距離 |
| 色 | 正常、注意、異常、未取得を区別する。色だけでなくアイコン・文字を併用する | 昼夜の実機視認性 |
| アイコン | ホーム、戻る、再生、音量等は一貫した意味を持たせる。不明瞭なものには名称を添える | 採用アイコンセット |
| 昼夜表示 | 明暗テーマと画面輝度を別設定として扱う。初期案は手動選択 | 輝度制御手段。自動切替用の信号は未定 |
| 文字あふれ | 曲名等は省略してもよいが、警告原因・操作名を判別できなくしない | 各領域の最大文字数・折返し |
| タッチ | 隣接操作の間隔を確保し、押下領域をアイコンの描画寸法だけで決めない | 実パネル寸法、タッチ精度 |
| 動き | 状態変化は即座に識別できるようにし、画面切替演出で後方映像表示を遅らせない | 切替方式と性能測定 |
| 単位 | 車速km/h、回転数rpm、温度degC、電圧Vなどを明示する | 小数桁数、表示幅 |

フォントサイズ・色コード・余白・タッチ領域寸法は共通定義で一元管理する。現時点で特定のピクセル値を製品仕様として固定しない。

<a id="dd-441"></a>
#### 4.4.1 デザインの方向性

| 観点 | 本システムで採用する方針 |
| --- | --- |
| 全体の印象 | すっきりした面と余白で情報を整理する。派手なグラデーション、立体的な飾りボタン、強い影は使わない |
| 主役となる情報 | ナビやカメラなど、現在選んだ機能を大きく表示する。詳細情報は必要なときだけ開く |
| 画面の区切り | 間隔、見出し、薄い区切り線を使う。全ての情報を箱で囲んだり、箱を入れ子にしたりしない |
| 操作位置 | よく使う操作を自作画面の下部にまとめる。画面ごとにボタン位置が変わらないようにする |
| 状態の表現 | 平常時は控えめに、録画停止など注意が必要な状態は文字と色で明確にする |
| 車両らしさ | コペンで取得できる情報と実装した機能だけを扱う。自動運転、周辺車両認識、空調操作、充電残量などを見た目のために追加しない |

参考資料：Tesla公式の[Model 3「タッチスクリーン」](https://www.tesla.com/ownersmanual/model3/ja_jp/GUID-518C51C1-E9AC-4A68-AE12-07F4FF8C881E.html)。上部の状態表示、ナビや車両状態の表示領域、下部からのアプリ操作という整理を参考にする。車種・ソフトのバージョンによって表示が異なるため、特定の画面の完全再現を目的にしない。

テスラの名称・ロゴ・専用アイコンを自作UIのブランドとして使用せず、コペン用の独自画面として作る。

<a id="dd-442"></a>
#### 4.4.2 色・文字・操作部品

以下は昼夜で比較するための初期配色案。実ディスプレイで文字の読みやすさとまぶしさを確認して調整する。

| 用途 | 昼間の淡色表示 | 夜間の暗色表示 |
| --- | --- | --- |
| 全体の背景 | 白に近い灰色 `#F5F5F5` | 黒に近い灰色 `#151515` |
| 操作領域・設定欄 | 白 `#FFFFFF` | 濃い灰色 `#242424` |
| 主な文字 | ほぼ黒 `#171717` | ほぼ白 `#F3F3F3` |
| 補足の文字 | 灰色 `#595959` | 明るい灰色 `#B8B8B8` |
| 選択中・操作の強調 | 青 `#2459C4` | 明るい青 `#8AB4FF` |
| 録画中などの正常状態 | 緑 `#216A42` | 明るい緑 `#7ACB9A` |
| 注意 | 黄土色 `#805300` | 黄色 `#F2C66D` |
| 異常・録画停止 | 赤 `#B3261E` | 明るい赤 `#FF9088` |

青・緑・黄・赤は必要な表示だけに使い、広い背景を色で塗り分けない。選択中は色に加えて印や名称でも区別する。警告は色だけで意味を伝えない。

| 項目 | 具体的な作り方 |
| --- | --- |
| 文字 | 日本語が読みやすいゴシック体を使う。太字は見出し・主要数値に絞り、極端に細い文字を使わない |
| 文字サイズ | 通常の説明、見出し、主要数値の順に大きくする。画面幅に合わせて文字を縮め続けず、配置や改行を調整する |
| アイコン | 家、矢印、再生、音量など意味が分かる記号を使う。線の太さと見た目を揃え、分かりにくい記号には短い名称を付ける |
| 選択操作 | 音量・明るさはスライダー、ON/OFF設定は切替スイッチ、表示方式は並べた選択肢を使う |
| 角の丸み | 操作部品や一時表示には控えめな丸みを付ける。初期案は8論理px以下とし、実寸は表示倍率を含めて確認する |
| 操作領域 | アイコンの絵が小さくても押せる範囲を確保する。見た目の余白を優先してタッチしづらくしない |
| 写真・映像 | 音楽画面は取得できたジャケット画像、カメラ画面は実映像を使う。背景装飾のために映像を暗くしたりぼかしたりしない |

「論理px」は、画面の表示倍率を考慮する前の寸法指定を指す。実際に何mmの大きさで見えるかは、採用ディスプレイで確認する。
昼夜のテーマ切替と実際の画面輝度は別設定とし、初期仕様は手動切替とする。

<a id="dd-443"></a>
#### 4.4.3 適用範囲と実機確認

- この方針は自作QML画面に適用する。OsmAnd・LIVIの内部画面まで同じ配色・部品配置に変更できるとは仮定しない。
- テスラのように地図と自作の操作領域を常時同じ画面へ表示する方式は、現時点では未確定。初期構成は外部アプリへの画面切替を維持する。
- 自作ホームに実際の地図を表示する場合は、表示方法・地図データ・利用条件を別途設計する。実装前に仮の地図を現在地のように表示しない。
- 見た目のために警告や未取得表示を消さず、リバースON時の後方映像を優先する。UI-05を理由に既存の操作制限を緩めない。
- 配色、文字、余白、操作領域はTheme.qmlなどの共通定義へまとめ、全画面で統一する。
- 昼間の反射、夜間のまぶしさ、長い日本語、手指による操作、4方向録画中の応答を確認して確定する。

QMLの注釈に挿入した挿絵はソフトの役割説明用であり、今回決めたデザインの完成見本ではない。具体的な画面見本はこの方針と実ディスプレイの条件に合わせて別途作成する。

<a id="dd-45"></a>
### 4.5 外部アプリ連携

| 対象 | 自作UIの役割 | 外部側へ委譲する内容 | 連携上の確認事項 |
| --- | --- | --- | --- |
| OsmAnd / Waydroid | 起動要求、準備・位置品質表示、画面切替要求 | 地図、目的地入力、経路探索、案内画面 | ホーム復帰、カメラ割込み、終了保存、位置失効時の表示 |
| LIVI | 接続状態、起動・表示要求、音声連携 | Android Auto画面と対応スマートフォン機能 | 再接続時にどの画面を表示・操作対象にするか、割込み、接続解除 |
| Mopidy | 自作UIからの再生操作と状態表示 | 音楽ライブラリ・プレイヤー機能 | Mopidy APIの接続、再生状態の同期、ホーム復帰 |

画面切替はScreenControllerが決定し、各連携担当ソフトは起動完了だけを理由に手前に表示しない。
画面を開く依頼には通し番号を付ける。古い依頼の完了通知は相手ソフトの状態確認には使うが、今表示したい画面を勝手に変えない。
外部画面からのホーム復帰・後方映像割込み・重要警告の通知は実機受入条件とする。
実現手段が未検証の場合は外部アプリを統合UIとして運用可能と判断しない。

<a id="dd-5"></a>
## 5. データ・設定設計

AppStateはselected_screen、effective_screen、previous_screen、reverse_validity、service_health、warning_listを保持する。
UIが保存する利用者設定は、明暗テーマ、アニメーション、起動画面、水温・低電圧警告値と`schema_version=1`。`preferences.json`と同じディレクトリの一時ファイルを同期して置き換える。保存範囲・初期値・制限は[付録9](../付録9_UI追加機能導入手順.md)を参照する。音量はMopidyの実値を読み戻し、UI設定には保存しない。リバースON、車速、警告確認状態も次回起動へ引き継がない。
UI更新周期、画面サイズ、タッチ領域寸法は実ディスプレイで決める。

<a id="dd-51"></a>
### 5.1 表示データ一覧

更新周期は画面再描画周期ではなく、元担当ソフトの観測周期・有効期限と分けて決める。
受信頻度が高くても測定時刻が古い値は失効させる。具体的な周期・桁数・期限は実測後に確定する。

| データID | 内容・表示先 | 取得元 | 更新契機 | 未取得・期限切れ時 |
| --- | --- | --- | --- | --- |
| DATA-TIME | 時計 / 共通領域 | OS時計・同期状態 | 秒または分が変わる時点。秒まで表示するかは未確定 | 未同期を識別可能にする |
| DATA-REC | 方向別録画状態 / 共通・カメラ | 06 カメラ表示・録画 | 状態変更と定期状態通知 | 状態不明。録画中の表示を残さない |
| DATA-UPLOAD | 未送信件数・容量 / 状態詳細 | 07 Google Driveアップロード・削除 | 台帳状態変更 | 未確認。未送信件数を0にしない |
| DATA-POS | GPS/補正/未測位 / 共通・ナビ待機 | 03 現在地補正、04 Linux位置情報連携 | 推定・連携状態変更 | 未測位または期限切れと表示 |
| DATA-SPEED | 車速km/h / 車両情報 | 09 OBD2車両情報取得 | 有効な観測受信 | 数値を「—」にし、停止判定へ流用しない |
| DATA-RPM | 回転数rpm / 車両情報 | 09 OBD2車両情報取得 | 有効な観測受信 | 未対応・未取得・期限切れを区別 |
| DATA-COOLANT | 車両水温degC / 車両情報 | 09 OBD2車両情報取得 | 有効な観測受信 | 数値を「—」にし理由を表示 |
| DATA-VOLTAGE | 電圧V / 車両情報 | 09 OBD2車両情報取得 | 有効な観測受信 | 未取得表示。ECU/アダプタ由来を区別 |
| DATA-REVERSE | リバース / 画面制御 | 15 サブコントローラ1後方系 | 変化通知・有効性変更 | UNKNOWN。OFFと扱わない |
| DATA-FRAME | 映像 / カメラ・俯瞰 | 06 カメラ表示・録画、08 サラウンドビュー | 有効期限内の画像を受信 | 映像未取得表示。古い画像を現在画像にしない |
| DATA-AUDIO | 曲名・再生・音量 / 音楽 | 12 オーディオ連携 | プレイヤー状態変更 | 未接続とし操作を制限 |
| DATA-HEALTH | CPU温度・冷却ファン回転数 / 警告・状態詳細 | 10 冷却ファン制御 | 観測・異常通知 | 回転数が取得できない場合は監視不能として表示する |
| DATA-APP | ナビ・Android Auto準備状態 | 02 Waydroidナビ管理、11 LIVI連携 | 接続・起動状態変更 | 機能ごとに準備中/利用不可を表示 |

車速の内部m/sから表示km/hへの変換はUI境界で行う。表示用に丸めた0 km/hを、停車許可の判断材料にしない。

<a id="dd-52"></a>
### 5.2 UI状態・設定の管理

| データ | 型・値の案 | 保持方針 |
| --- | --- | --- |
| 選択した通常画面（selected_screen） | 画面ID | 利用者が選んだ通常画面。表示中画面と分離 |
| 実際の表示画面・カメラ表示方法（effective_screen / camera_mode） | 画面ID / 通常（NORMAL）・後方優先（REAR_PRIORITY）・信号不明（SIGNAL_UNKNOWN） | 現在表示している内容。起動ごとに初期化 |
| 割込み前の画面（previous_screen） | 画面IDまたは未設定 | 割込み前の復帰先。初回だけ保存し、反復ON通知で上書きしない |
| リバース情報が利用可能か（reverse_validity） | 有効（VALID）・期限切れ（STALE）・不明（UNKNOWN）・異常（FAULT）等 | リバース値と分離し、失効時にOFFへ置き換えない |
| 担当ソフトの動作状態（service_health） | 担当ソフトID別の状態・理由・最終観測 | 対象機能の操作可否と未準備・異常表示に使用 |
| 画面要求の通し番号（request_generation） | 画面要求を出すたびに増やす番号 | 古い依頼の完了通知で、今表示したい画面を変えない |
| 走行・停車の状態（motion_state） | 停止（STOPPED）・走行中（MOVING）・不明（UNKNOWN） | 元データと期限から判定。次回起動へ引き継がない |
| 結果待ちの操作（pending_commands） | command_idと処理状態 | 上限を設け、画面破棄後も結果を誤適用しない |
| 警告一覧（warning_list） | 発生元・コード・重要度・発生状態・確認済み | 原因状態と利用者の確認状態を分離 |
| 適用済み設定（`uiFeatures.settings`） | テーマ、アニメーション、起動画面、警告閾値 | 型・範囲・バージョンを検証して保存 |
| 編集中の設定（`uiFeatures.draft`） | 設定の編集コピー | 適用完了まで確定値と分離 |

起動時に保存設定が壊れている場合は検証済みの既定値でUIを起動し、設定読込異常を記録する。
リバース、車速、操作許可、未完了の車体操作を前回状態から復元しない。

<a id="dd-6"></a>
## 6. 処理・画面の切替

1. 通信状態と有効期限を更新し、画面候補を評価する。
2. 有効なリバースONでは後方カメラを優先する。映像がなければ未取得を明示し、過去画像を現在画像に見せない。
3. サラウンドは08 サラウンドビューの利用許可がある場合だけ表示する。
4. 警告は必要に応じて画面に重ねて表示し、後方映像全体を不必要に隠さない。
5. リバースOFFの有効な通知で通常画面へ戻す。通信断はOFFと見なさず警告付き退避画面へ移る。
6. Waydroid / LIVIからの遅い起動完了で、優先カメラ画面を奪わない。

画面状態はBOOTSTRAP、HOME、NAVIGATION、ANDROID_AUTO、CAMERA、SURROUND、AUDIO、VEHICLE、SETTINGS、REAR_CAMERAとする。[画面一覧](#dd-41)のUI-REARはREAR_CAMERAとして扱う。UI-WARNINGは独立した状態として現在画面へ合成する。

#### 6.1.1 画面切替の優先順位と割込み

画面切替の判断は`ScreenController`へ集約する。QMLは画面IDを要求するだけで、外部ソフトの起動・停止やGPIO操作を直接行わない。通常画面の優先順位は、ホーム、ナビ、カメラ、音楽、車両情報、設定の順に管理し、バックカメラは最優先の`REAR_CAMERA`として扱う。

```mermaid
flowchart TB
    Input["タッチ操作・車両信号"] --> Controller["ScreenController\n画面切替判定"]
    Controller --> Priority{"優先順位と\n切替許可を確認"}
    Priority -->|通常| Transition["TRANSITIONING"]
    Priority -->|リバースON| Rear["REAR_CAMERA"]
    Priority -->|不許可| Warning["現在画面を維持\n警告を表示"]
    Transition --> State["AppStateを更新"]
    Rear --> State
    State --> QML["QML画面を表示"]
    QML --> Done["IDLE"]
```

有効なリバースONを受信した場合は、初回だけ現在の通常画面を`previous_screen`へ保存し、後方カメラ画面へ切り替える。リバース中の通常画面要求は拒否する。リバースOFFを受信したら、保存した画面が利用可能か再確認して復帰し、利用できなければホームへ戻す。リバース信号が不明・期限切れの場合はOFFとは扱わず、後方画面を自動解除しない。

切替中は`TRANSITIONING`状態とし、同時に到着した要求を重複実行しない。切替完了前に別要求が来た場合は、優先順位が同等以上の最新要求だけを1件保留し、現在の切替完了後に処理する。WaydroidやLIVIの起動完了通知が遅れて届いても、現在の優先画面を変更しない。

通常画面間はQMLのフェード・短時間スライドを使用する。後方カメラと重要警告への切替は、アニメーション完了を待たず表示を更新する。外部ソフトの操作結果は`command_id`で照合し、結果を受信するまで外部画面の切替完了とは判定しない。

<a id="dd-61"></a>
### 6.1 画面切替図

通常選択とリバース割込みを分けて示す。警告はどの画面にも重ねて表示するため、別の切替先画面としては描かない。
UI-NAV / UI-AAへの切替は起動待ち画面を含み、外部アプリ準備後の手前への表示にも優先順位判定を適用する。

```mermaid
flowchart TB
    Boot["UI-BOOT 起動状態"] --> Home["UI-HOME ホーム"]
    Home --> Normal["通常選択画面<br/>ナビ・Android Auto・音楽<br/>カメラ・車両情報・設定"]
    Normal -->|"ホーム操作"| Home
    Home -->|"有効なリバースON"| Rear["UI-REAR 後方優先"]
    Normal -->|"有効なリバースON"| Rear
    Rear -->|"有効なリバースOFF"| Restore["保存した通常画面を再評価"]
    Restore -->|"復帰可能"| Normal
    Restore -->|"未保存・利用不可・ホーム"| Home
    Rear -->|"信号期限切れ・通信断"| Unknown["カメラ退避表示<br/>リバース状態不明"]
    Unknown -->|"有効なON"| Rear
    Unknown -->|"有効なOFF"| Restore
    Normal -->|"停止・駐車条件と利用許可"| Surround["UI-SURROUND"]
    Surround -->|"有効なリバースON"| Rear
    Surround -->|"条件喪失・終了操作"| Home
```

後方映像の取得失敗だけでリバース優先を解除しない。UI-REAR内で未取得を表示する。
信号不明時の退避表示はCAMERAのSIGNAL_UNKNOWNモードとし、自動で通常画面へ戻さない。有効な最新後方映像がある場合は状態不明の警告とともに表示し、映像も無効なら未取得表示にする。
起動時・俯瞰表示中もリバース割込みを受理できるようにする。図の通常の画面切替よりも、後方映像への切替判断を優先する。

<a id="dd-62"></a>
### 6.2 操作・通知への対応と優先順位

| 操作・届いた通知 | 確認する条件 | 行う処理 |
| --- | --- | --- |
| UI初期化完了 | 画面表示に必要なモジュールが準備できている | ホームへ。未準備担当ソフトは個別に表示 |
| 通常画面選択 | 操作許可と現在の割込み状態 | 表示要求を更新し、必要なら担当ソフト起動 |
| リバースON | 送信元・順序・期限が有効 | 初回だけ復帰先を保存し後方優先へ |
| リバースON再通知 | すでに後方優先 | 状態の鮮度を更新し、復帰先は維持 |
| リバースOFF | 信号が有効 | 復帰先の利用可否と操作制限を再評価 |
| リバース信号失効 | 後方優先中または信号不明中 | カメラ退避表示を維持し警告 |
| 外部アプリ準備完了 | 画面要求の通し番号が一致し、今も表示したい画面である | 手前に表示する依頼。条件不一致なら背景で待機 |
| 俯瞰許可取消 | 車速・駐車条件・映像品質を確認 | 俯瞰を終了し、後方優先条件を再評価。該当なしはホーム |
| 担当ソフトとの通信断 | 機能別に評価 | 画面内で異常を表示し、危険な操作を無効化 |
| OS停止通知 | 終了処理中 | 新しい操作を止め、設定を保存し、状態通知・映像の受信を終了する |

実際に画面を切り替える直前にも条件を確認する。他ソフトへ処理を依頼した時点では許可されていても、その後にリバースONなどの変化があれば判断し直す。
優先順位は後方優先、許可された俯瞰、通常選択の順とし、警告は重要度に応じて画面に重ねて表示する。警告の全面表示を初期仕様にしない。

<a id="dd-7"></a>
## 7. 異常処理

相手ソフトから返事がなければ該当機能だけを利用不可にし、接続が回復したら現在の状態を送り直してもらう。
画面操作を担当する処理で、通信の返事待ち・動画の展開・データベース全体の検索を行わない。表示待ちデータの件数には上限を設け、古い値を残し続けない。

<a id="dd-71"></a>
### 7.1 状態別表示・復旧動作

| 状態 | 表示内容の例 | 操作・復旧方針 |
| --- | --- | --- |
| 起動・読込中 | 「ナビを起動中」「接続を確認中」 | 対象機能の重複起動を抑制。他画面は利用可能 |
| 値の未取得 | 「未取得」または「—」と理由 | 有効な新規観測を受信して復旧。0表示にしない |
| 未対応項目 | 「この車両では未対応」 | 対応確認済みの場合だけ表示。一時無応答と区別 |
| カメラ断・期限切れ | 「後方映像を取得できません」等 | 古い映像を取り除く。リバースONなら優先画面は維持 |
| リバース信号不明 | 「リバース状態を確認できません」 | OFF扱いしない。カメラ退避表示と最新信号待ち |
| 録画停止 | 方向と停止理由 | 録画中表示を解除。映像表示が可能なら表示は継続 |
| クラウド送信失敗 | 「録画は本体に保存されています」 | ローカル保存を確認できる場合のみ、この文言を使う |
| 保存容量不足 | 残容量・録画への影響 | 警告。未アップロード録画をUI判断で削除しない |
| ナビ位置失効 | 「現在地を確認できません」 | 地図閲覧は継続可能。補正位置を新しいGPS実測と表示しない |
| 外部アプリ停止 | 「ナビを利用できません」等 | 優先カメラがなければ自作の状態画面へ戻す |
| 操作結果不明 | 「操作結果を確認できません」 | 状態を再取得。成功表示・無条件再送をしない |

同じ警告は発生元とコードでまとめ、通知の連発を避ける。発生継続・回復・再発を区別する。
確認ボタンを押しても原因を解消したことにはしない。ログと現在表示の両方に復旧状況を反映する。

上部の操作エラーは一行目に対象機能と失敗した操作、二行目に原因を表示する。例は「LIVIの画面表示に失敗しました。」「原因: LIVIウィンドウをSwayから確認できませんでした」。OsmAnd、LIVI、OBD2などのサービス名と操作名を通信応答から引き継ぎ、「操作に失敗しました」だけの表示にしない。音楽、録画設定、Google Drive送信切替などUI内部の非同期処理も対象操作を明記する。

上部バーに収まらない文は省略表示し、「詳細」から警告履歴へ移る。履歴ではエラー文を折り返して全文表示し、長文に応じて項目の高さを伸ばす。原因が通知されていない場合はその旨を表示し、故障箇所や対処を推測して断定しない。サービスの文字列は装飾付きHTMLとして解釈せず、通常の文章として表示する。

## 8. 起動・終了・運用設計

Raspberry Pi 5実機およびDebian 13仮想環境ではブラウザを使用せず、PySide6/QMLのネイティブ画面としてSway Waylandセッション上で起動する。画面全体の座標系を固定し、ナビ表示領域の`x`、`y`、`width`、`height`をUI設定からWaydroidナビ管理へ渡す。OsmAndとLIVIは同じWaylandコンポジタ上の外部ウィンドウとして扱い、Swayの移動・リサイズ機能でその領域へ配置する。Wayland外部サーフェスの完全埋込みは将来検討とする。VirtualBoxのGNOMEセッションは対象外とし、Swayセッションで実機と同じ配置方式を確認する。
終了時は新しい操作を止め、設定を保存し、状態通知・映像の受信を終了する。UIを閉じただけでは、録画用ソフトやOSは停止しない。

<a id="dd-81"></a>
### 8.1 操作制限・利用条件

以下は初期設計案であり、実車運用前に検証・確定する。車速不明や期限切れを停止中と見なさない。
STOPPEDの成立条件は、有効な未丸め車速、連続確認時間、必要な車両信号を用いて別途確定する。
サラウンドにはSTOPPEDだけでなく、08 サラウンドビューが管理する駐車条件・利用許可も必要とする。

| 操作 | 停止確認時 | 走行中 | 車両状態不明 |
| --- | --- | --- | --- |
| 音量・再生/一時停止 | 利用可能 | 最小限の操作に限定する案 | 最小限の操作に限定する案 |
| ホーム・通常画面への切替 | 利用可能 | 切替機能と操作数を検証して確定 | 同左 |
| 目的地入力・詳細選曲 | 利用可能 | 自作UIからの入口を制限する案 | 変更操作を制限する案 |
| 設定変更 | 利用可能 | 禁止する案 | 禁止する案 |
| カメラの手動切替 | 利用可能 | 制限する案 | 制限する案 |
| 後方映像の自動表示 | 有効なリバースONで表示 | 有効なリバースONで表示 | リバース信号自体が有効なら表示 |
| サラウンド表示 | 駐車条件・映像品質も確認して許可 | 禁止 | 禁止 |
| ドアロック操作 | 初期リリースでは無効 | 無効 | 無効 |

リバース優先中は停車判定に関係なく、ホーム・戻る・手動方向切替による後方映像からの離脱を禁止する。
操作許可は部品表示時と要求送信時の両方で判定する。操作中に条件を失った場合は、未送信の編集・操作を停止する。
外部アプリ内のタッチ操作まで自作UIが制限できるとは仮定しない。OsmAnd・LIVI側の動作を含めて検証し、制限できない機能の扱いを運用仕様で確定する。

## 9. 試験・受入条件

| 試験 | 受入条件 |
| --- | --- |
| ナビ起動遅延 | ホーム操作・カメラ表示が待たされない |
| 通知の到着順が逆の場合 | 古いリバースOFFで新しいONを上書きしない |
| 画面競合 | リバース中のナビ起動完了で画面が切り替わらない |
| データ期限切れ | 車速・温度・位置が未取得として識別できる |

| 画面切替管理の個別試験 | 通信・データ管理を模擬した試験用部品で、操作許可、表示優先順位、元画面の記憶を確認できる |
| 通信結果の受渡し | 裏で動く通信処理から画面データを直接書き換えず、画面操作側で通知の順序・期限を確認して反映する |
| 受信する映像の切替 | 切替前の映像を新画面へ表示しない。表示側が画像の使用を終えても録画は継続する |
| 終了中の遅延応答 | 破棄済み画面や状態へアクセスせず、終了待ちの期限切れを記録する |

<a id="dd-91"></a>
### 9.1 性能目標・画面受入試験

以下の時間目標は測定前の仮目標であり、達成済み仕様ではない。解像度・4方向録画負荷・ネットワーク条件を固定して測定し、採用値を決める。

| 試験ID | 対象・測定区間 | 仮目標・判定内容 |
| --- | --- | --- |
| UIT-01 | タップ受付から押下/待機状態の表示まで | 100 ms以内を仮目標。UIとは別に動くソフトの完了時間とは別 |
| UIT-02 | 有効なリバース通知受信から後方優先領域の表示まで | 300 ms以内を仮目標。映像未着なら未取得表示 |
| UIT-03 | 実際のリバース信号変化から最初の有効期限内の後方映像まで | 数値は未確定。入力保護・安定判定・通信・撮影・描画の全遅延を実測 |
| UIT-04 | データ有効期限経過から無効表示まで | 100 ms以内を仮目標。データ自体の期限は送信元別に確定 |
| UIT-05 | 4方向録画・アップロード・ナビ併用 | 操作不能にならず、処理待ちデータが増え続けない。負荷条件・継続時間は未確定 |
| UIT-06 | 昼夜、長い曲名、最大警告文、未取得表示 | 重要文字・操作領域が重ならず、色だけに依存しない |
| UIT-07 | 外部アプリ表示中のリバースON | 後方表示へ切替可能。外部アプリが再び手前へ出て、後方映像やタッチ操作を妨げない |
| UIT-08 | リバースON反復、OFF、信号断、再接続 | 復帰先が壊れず、古いOFF通知で後方優先を解除しない |
| UIT-09 | 状態別操作制限 | STOPPED / MOVING / UNKNOWNと後方優先を組み合わせて検証 |
| UIT-10 | 設定適用失敗・破損設定・再起動 | 適用済み状態を偽らず、検証済み既定値で復旧できる |

表示切替時間と、映像を撮影してから表示するまでの経過時間を別々に記録する。
試験記録にはOS・ソフトのバージョン、ディスプレイ条件、データ観測/受信/表示時刻、負荷、期待結果、実結果を残す。
複数機器の時刻を比較する試験では同期誤差を確認し、誤差不明のまま遅延目標達成と判定しない。

## 用語の注釈

本文の「注1」などをクリックすると、対応する説明へ移動する。プログラムの名前や図の接続関係を変えないよう、注釈番号は本文に付ける。

<a id="note-qml"></a>
### 注1 QML（キュー・エム・エル）

画面の見た目や、操作したときの動きを記述するための言語。ボタンの配置、文字・色・画像、タッチ操作への反応などを書く。画面定義は主に拡張子が`.qml`のファイルに保存する。

今回の設計では、QMLは表示とタッチ操作の受付を担当し、表示する画面の判断や他ソフトへの指示はPython側が担当する。QMLをPythonの代わりに使うのではなく、役割を分けて組み合わせる。

![QMLで画面の配置を決め、Pythonがリバース信号から表示内容を判断し、Qtがディスプレイへ表示する関係](images/qml_python_qt_roles.png)

図 注1-1 QML・Python・Qtの役割と、リバースONで後方映像を表示する例

QMLが画面の配置を決め、Pythonが表示内容を判断する。その両方を使ってQtが実際の画面を表示し、PythonとQtの連携にはPySide6を使う。QMLからPythonへ順番に変換する、という意味ではない。
図の映像はカメラ担当ソフトから受け取るもので、QMLが撮影するわけではない。画面内のボタンや配置は役割説明用のイメージであり、実際に採用する画面デザインは別途決める。

例えば音楽の再生操作は、次の順序で動く。

1. QMLが再生ボタンを表示する。
2. タッチされたことをPython側へ伝える。
3. Python側が音楽担当ソフトへ再生を依頼する。
4. 再生が始まったことを確認し、QMLの表示を一時停止ボタンへ変える。

<a id="note-qt"></a>
### 注2 Qt

画面を持つアプリを作るための開発用の仕組み。画面の表示、ボタンや文字の描画、マウス・タッチ操作の受付などに必要な機能を提供する。

QMLは画面の内容を書く言語であり、Qtはその画面を動かすために利用する仕組み、という関係になる。

<a id="note-pyside6"></a>
### 注3 PySide6（パイサイド・シックス）

PythonからQt 6の機能を利用するためのライブラリ。ライブラリとは、プログラムから呼び出して利用できる機能をまとめたもの。

今回の設計では、Pythonで画面アプリを起動し、QMLへ車速や再生状態を渡したり、QMLからタッチ操作を受け取ったりするために使う。QML・Qt・PySide6は別々の役割を持ち、組み合わせて1つの画面アプリを作る。
