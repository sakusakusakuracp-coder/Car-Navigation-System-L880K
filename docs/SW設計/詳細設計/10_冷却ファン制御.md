## 1. 目的・適用範囲

12V動作の4ピンPWM冷却ファン1台を、Pi 5のPWM出力で制御する。PWM周波数は標準仕様に合わせて25kHzを初期値とし、許容範囲を21kHz-28kHzとする。同じ冷却ファンのTACHを取得し、CPU温度に応じた冷却と回転監視を行う。

筐体制約により冷却ファンは1台とする。通知にはその冷却ファンの回転数だけを含め、存在しないファンの状態を推測・通知しない。

温度取得異常・高温・冷却ファンの回転異常時は、検証済みの駆動方式で最大冷却を要求する。プロセス停止やOS停止時の冷却継続はソフト単独では保証できない。閾値・駆動段・停止時出力が未確認なら自動制御を有効にせず、回路側の既定冷却を確認する。

## 2. 要求仕様・役割

機能は実現する動作、モジュールは処理の分担、関数はモジュール内の処理単位を表す。本書の関数名・通知名は実装内部の契約であり、採用ライブラリの標準APIと区別する。

<a id="dd-functions"></a>

### 2.1 機能一覧

| 機能ID | 機能 | 実現する動作 |
| --- | --- | --- |
| FAN-F01 | 制御条件と端子の確認 | **開始条件・入力：** ファン型式、PWM周波数、反転論理、PPR、温度表、端子割当を読み込む。<br/>**確認・処理：** 採用Pi 5のPWM方式と端子の競合を確認する。GPIO番号とOS内のチップ番号を同じ番号と仮定しない。<br/>**処理結果：** 検証済みプロファイルでのみ自動制御を開始し、不明な波形を出力しない。 |
| FAN-F02 | CPU温度と回転数の取得 | **開始条件・入力：** CPU温度のOSインターフェースと冷却ファンのTACHエッジを受け取る。<br/>**確認・処理：** 温度の出所・単位・期限を確認する。TACHは採用した片側エッジを数え、測定窓とPPRから回転数を求める。<br/>**処理結果：** 温度とファン回転数を品質付きで渡す。存在しないファンの値は生成しない。 |
| FAN-F03 | 温度に応じたPWM指令 | **開始条件・入力：** 有効なCPU温度、前回指令、温度帯設定を使用する。<br/>**確認・処理：** 温度表とヒステリシスで目標を選び、通常時の急な指令低下を抑える。始動に必要な指令と最低継続デューティを区別する。<br/>**処理結果：** 1台のファンへの指令をPwmDriverへ渡す。初期段階は温度対デューティ表で動かす。 |
| FAN-F04 | ファン回転監視と回転数制御 | **開始条件・入力：** ファンの回転数、PWM指令、始動猶予、目標回転数を使用する。<br/>**確認・処理：** 回転要求がある時だけ停止・低回転を判定する。閉ループ段階では承認済み係数で回転誤差を補正し、補正量と積分量を制限する。<br/>**処理結果：** 1台のファンへ補正指令を出す。TACH不明なら閉ループを停止し冷却優先へ移る。 |
| FAN-F05 | 異常時の冷却と警告 | **開始条件・入力：** 高温、温度取得失敗、TACH異常、PWM設定失敗、制御周期遅延を検知する。<br/>**確認・処理：** 温度低下側の変化制限より異常時の冷却を優先する。最大指令の要求・OS設定成功・回転確認を別状態で管理する。<br/>**処理結果：** CPU温度、ファンの監視結果、冷却異常をUIへ通知し、承認済み経路へ負荷低減を要求する。 |
| FAN-F06 | 停止と再開 | **開始条件・入力：** サービス停止、設定変更、OS再開を受け取る。<br/>**確認・処理：** 正常終了時の端子状態を検証済み回路プロファイルに従って扱う。無条件にPWM無効化・GPIO解放を行って最大回転を仮定しない。<br/>**処理結果：** 終了結果を通知する。再開時は温度・回転・PWM所有権を取り直し、過去の積分値を使わない。 |

## 3. 内部構成

5モジュールに分ける。制御判断は単一の周期処理で行い、GPIOイベントと温度値は測定時刻付きで受け渡す。PWM波形をPythonのsleepループで生成する方式は採用しない。

### 3.5 モジュール詳細

温度・TACH・PWMを模擬できる境界を設ける。実GPIOを使わない単体試験で反転・異常優先・計算を確認してからベンチ試験へ進む。

<a id="dd-module-1"></a>

#### 3.5.1 TemperatureReader（CPU温度の取得）

| 項目 | 内容 |
| --- | --- |
| 入力 | OSのCPU温度情報 |
| 出力 | degC、測定時刻、品質 |
| 保持情報 | センサー識別、直近値と期限 |
| 処理 | thermal zoneの番号だけで決めずtype等と機器構成で確認。単位変換は入口で一度だけ行う |
| 関数 | read_temperature |
| 異常時 | 読取失敗・不正値・期限切れを通知し、前回低温値を有効のまま残さない |

<a id="dd-module-2"></a>

#### 3.5.2 TachCounter（冷却ファン回転数計測）

| 項目 | 内容 |
| --- | --- |
| 入力 | BCM20に対応する入力エッジと時刻 |
| 出力 | RPM、計測窓、パルス数、品質 |
| 保持情報 | PPR、片側エッジ、イベント連番、有限パルス履歴 |
| 処理 | エッジを数えて実際の計測秒数からRPMを計算。イベント欠落と真のパルス0を区別 |
| 関数 | record_edge、calculate_rpm |
| 異常時 | 溢れ・順序異常・入力切断はRPM不明。停止を推測しない |

<a id="dd-module-3"></a>

#### 3.5.3 ControlPolicy（冷却目標と異常判断）

| 項目 | 内容 |
| --- | --- |
| 入力 | 温度、RPM、前回指令、運用設定 |
| 出力 | 共通ファン指令、状態、警告 |
| 保持情報 | 温度帯、始動猶予、異常フラグ、積分値、指令世代 |
| 処理 | 異常優先、通常温度表、承認後の回転補正の順。復帰は正常継続を確認 |
| 関数 | validate_profile、select_target、check_rotation、adjust_feedback、enter_failsafe |
| 異常時 | 温度不明・高温・回転異常は検証済み最大冷却。出力方式不明では波形を推測しない |

<a id="dd-module-4"></a>

#### 3.5.4 PwmDriver（PWMの出力）

| 項目 | 内容 |
| --- | --- |
| 入力 | 有効デューティ、25kHz（21kHz-28kHz）、駆動段プロファイル |
| 出力 | 要求値とOS設定結果 |
| 保持情報 | PWM実デバイス・チャネル、極性、最後の適用世代 |
| 処理 | Linux PWM sysfsのPWMデバイスとチャンネルを確認して専有。lgpioはTACH入力だけに使用し、PWM波形には使用しない。外部駆動段の反転はこの層で吸収 |
| 関数 | initialize_pwm、apply_duty、stop_fan_control |
| 異常時 | 設定失敗はDRIVER_FAULT。読み戻しを物理波形の証明にしない |

<a id="dd-module-5"></a>

#### 3.5.5 FanHealthPublisher（状態・警告の通知）

| 項目 | 内容 |
| --- | --- |
| 入力 | 温度、RPM、指令、設定結果、異常 |
| 出力 | fan.statusと負荷低減要求 |
| 保持情報 | boot_id、sequence、最新状態と理由 |
| 処理 | 1台のファン計測を明示。最大要求中でも回転不明なら冷却正常と表示しない |
| 関数 | publish_health |
| 異常時 | 通知先停止でも制御を続け、無期限通知キューを作らない |

<a id="dd-function-flows"></a>

### 3.7 関数のフローチャート

デューティはファン入力端子での有効比率を0～1で表す。GPIOのHIGH比率と混同せず、PwmDriverでのみ変換する。例外処理も冷却要求と実際の出力結果を分ける。

<a id="dd-os-api"></a>

### 4.2 OS入力・PWM実装

TemperatureReaderはLinuxのthermal zone等からCPU温度を読み、typeと採用機器で対象を確認する。ゾーン番号を固定するだけの実装は避け、採用ABIの単位を確認してdegCへ変換する。[Linux thermalインターフェース](https://www.kernel.org/doc/html/latest/driver-api/thermal/sysfs-api.html)

PwmDriverはLinux PWM sysfsの`pwmchip`と`pwmN`を使用する。25kHzの周期は40,000ns、デューティは0-40,000nsへ変換する。`lgpio.tx_pwm`はソフトウェアPWMのため4ピンPWMファンの25kHz出力経路には使用しない。PWMチップとチャンネルはPi 5の実機で確認し、設定した周波数・デューティはオシロスコープまたは周波数計で測定する。OSの設定値読戻しだけでは物理波形を保証できない。[Linux PWMインターフェース](https://www.kernel.org/doc/html/latest/driver-api/pwm.html)

TachCounterはlgpioのGPIOエッジイベントを使用する。採用API・GPIOチップ・ライン番号・イベント時計は実機で確認する。BCM20がそのままgpiochipのoffsetになるとは決めつけない。PWM GPIOをlgpioの別PWMや他ソフトが同時に駆動しない。

本ソフトから強制的にプロセスを終了したり、電源遮断したりしない。OSの温度保護機能は無効化しない。UIの音楽・画面操作より冷却判断を優先するが、利用者の直接GPIO操作口は設けない。

| TemperatureSample | センサーID、値、観測時刻、期限。前回正常値と現在の取得成否を分離 |

<a id="dd-rpm"></a>

### 5.2 回転数の計算と品質

```text
rpm = 60 * pulse_count / (pulses_per_revolution * window_seconds)
rpm_step = 60 / (pulses_per_revolution * window_seconds)
```
数えるのは立上りまたは立下りのどちらか一方。両エッジを数えるならPPRとの関係が変わるため、片側を初期方式とする。PPRは型式で確認し、一般例の2を無断で固定しない。

パルス0は、有効な計測窓と入力回路が成立した場合に限り0 rpmとして計算できる。入力断線や計測処理停止ではRPM不明となる。また回転要求中のパルス0だけでは機械停止とTACH断線を確定できないので、STALL_SUSPECTEDまたはTACH_FAULTとして扱う。

最短エッジ間隔・ノイズ除去条件は最大回転数とPPRに合わせる。強すぎる除去で正しいパルスを落とさない。イベント取りこぼし・バッファ溢れを検出した窓では、少ないパルス数を実回転数として使用しない。

<a id="dd-control-law"></a>

### 5.3 PWM変換と段階的な回転制御

```text
fan_duty = clamp(command, validated_min, 1.0)

gpio_high_ratio =
    fan_duty                 # 非反転駆動
    1.0 - fan_duty           # 反転駆動

period_ns = 1_000_000_000 / pwm_frequency_hz
```
上記は外部駆動段の論理例であり、Linux側polarity設定との二重反転を避ける。実際の有効時間計算は採用APIの定義に合わせ、0%・中間・100%を波形と回転で確認する。停止可能なファンでも、0%で必ず停止するとは仮定しない。

段階1は温度対デューティ表とファン回転監視。段階2は温度対目標RPMとフィードフォワード指令にPI補正を加える候補とし、実機調整後だけ有効化する。

閉ループではP項・積分量・変化率を制限する。上限・下限でさらに飽和方向へ積分しない。始動中、TACH不良、指令変更、設定変更、長い周期欠落では積分を解除する。異常時の最大冷却要求は通常の上昇速度制限を迂回し、復帰後の急な低下は抑える。

## 6. 処理・状態遷移



<a id="dd-states"></a>

### 6.1 制御状態と異常の優先順位

```mermaid
stateDiagram-v2
 [*] --> CONFIG_CHECK
 CONFIG_CHECK --> STARTUP: 検証済み設定
 CONFIG_CHECK --> CONFIG_FAULT: 未確認・不正
 STARTUP --> NORMAL: 始動と入力確認
 STARTUP --> FAILSAFE: 入力・回転異常
 NORMAL --> FAILSAFE: 高温・取得異常
 FAILSAFE --> STARTUP: 正常継続と復帰条件成立
 NORMAL --> STOPPING: 終了
 FAILSAFE --> STOPPING: 終了
 CONFIG_FAULT --> STOPPING: 終了
 STOPPING --> [*]
```
FAILSAFEにTHERMAL_ALERT、SENSOR_FAULT、TACH_FAULT、DRIVER_FAULT等の複数理由を保持する。最も深刻な1件だけ表示して他の故障を消さない。CONFIG_FAULTでは駆動方式が不明なので、推測で100%波形を出さない。

優先順は駆動不能の通知、異常時最大冷却、始動、通常温度制御、承認済み回転補正とする。始動猶予はTACH判定のためであり、高温・温度取得異常を無視する猶予ではない。

<a id="dd-runtime"></a>

### 6.2 復帰・出力競合の扱い

異常解消は新しい正常測定が所定時間継続したことを確認する。古い正常値の再通知で復帰しない。閉ループへ戻る際は積分を初期化し、現在指令から滑らかに移行する。

異常通知で指令世代を進め、遅れて届いた通常デューティの設定要求をPwmDriverで拒否する。既に実行中のOS操作は取消可能とは限らないので、終了直後にも世代を照合して最大冷却要求を再適用する。

制御プロセスが固まった場合、ソフト内タイマーも動けない。監視再起動だけで冷却を保証せず、波形停止・固定レベル・GPIO解放・Pi無給電時の回路動作を別に評価する。

## 7. 異常処理

| 異常 | 出力と通知 |
| --- | --- |
| 温度取得失敗・期限切れ | 検証済み最大冷却を要求しSENSOR_FAULT |
| 高温・温度上昇継続 | 最大冷却、THERMAL_ALERT、承認済み負荷低減要求 |
| ファン低回転・パルスなし | 始動猶予後に異常。閉ループ停止・最大冷却要求 |
| TACH入力品質不良 | RPM不明。0 rpmや正常へ変換しない |
| ファン停止 | TACH異常または低回転として検出し、最大冷却要求と警告を出す |
| PWM書込失敗・所有競合 | DRIVER_FAULT。最大要求成功と表示しない |
| 周期遅延・OS休止復帰 | 古い入力と積分を破棄して初期冷却から再確認 |
| 状態通知先停止 | 制御は継続。最新状態だけ保持 |

<a id="dd-8"></a>

## 8. 起動・終了・運用設計

起動前に12V供給と駆動回路の既定状態を検証する。サービスはUIから独立して起動し、温度と回転を監視する。OS・カーネルが持つ別のファン制御と同じPWMチャネルを二重に使用しない。

正常終了では検証済み停止プロファイルを適用し、最後の要求と設定結果を記録する。PWMをdisableすればファンが最大回転になる、またはenableを保持すればプロセス終了後も継続する、と一律には決めない。

ファンの12Vが常時給電ならOS停止後も回り続けてバッテリーを消費する可能性がある。停止後の必要冷却時間と待機消費はハードウェア電源設計と合わせて決める。ソフト無動作時に止める必要があるなら、ソフトだけに依存しない電源・制御機構を検討する。

## 用語の注釈

| 用語 | 意味 |
| --- | --- |
| PWM | 一定周期でON/OFFし、有効な時間の比率で指令する信号 |
| TACH / PPR | 回転に応じたパルス出力と1回転あたりのパルス数 |
| ヒステリシス | 温度上昇時と下降時で切替条件を変え、頻繁な切替を防ぐこと |
| 閉ループ制御 | 実測RPMと目標RPMの差を使って指令を調整する方法 |
| 積分の制限 | 指令が上限等に張り付いた時に補正量が増え続けるのを防ぐ処理 |
| フェイルセーフ | 異常時に冷却を優先する設計。ソフトだけでは保証できない範囲がある |
