## 1. 目的・適用範囲

Raspberry Pi 5のUSBポートに接続したUSB–OBD変換ケーブルを通し、車体側はK-LineでL880KコペンのECUから車両情報を取得する。01 カーナビUI、03 現在地補正、08 サラウンドビュー等へ値・取得可否・出所・鮮度を通知する。

通信経路は「Pi 5 → USBシリアル → K-Line対応USB–OBD変換ケーブル → 車体OBDコネクタ → K-Line → ECU」とする。USB側の転送方式と車体側の診断プロトコルを分け、CAN通信を使用する設計にはしない。GPIOへ車体通信線を直接接続しない。

K-Lineは車体側の通信線・電気方式を示し、それだけで要求データや換算式は決まらない。L880K用の初期化・フレーム形式・データ識別子を確認済みプロファイルとして持つ。汎用の標準OBD-II PIDやpython-OBDで取得できる前提は採用しない。

車両制御、ECU書換え、故障コード消去は対象外。診断通信の開始・維持と確認済みデータ読取に必要な送信だけを許可する。バックギア・ウィンカーは担当サブコンの信号を利用し、未取得の車速をGPS速度で埋めてECU車速として配信しない。共通基盤のソースは初期実装済み、実車適合試験は未実施。

## 2. 要求仕様・役割

機能は実現する動作、モジュールは処理の分担、関数はモジュール内の処理単位を表す。本書のソース構成は初期実装へ反映済みであり、採用ライブラリの標準APIと区別する。L880K固有の通信プロファイルが未確定のため、初期実装は未確認の車体コマンドを送信しない。

<a id="dd-functions"></a>

### 2.1 機能一覧

| 機能ID | 機能 | 実現する動作 |
| --- | --- | --- |
| OBD-F01 | USB接続とK-Line通信の開始 | **開始条件・入力：** 承認済みUSB識別情報、シリアル設定、L880K用K-Lineプロファイルを読み込む。<br/>**確認・処理：** 同じアダプタの排他的利用と対象の一致を確認する。自動探索で関係のないUSBシリアル機器へ診断要求を送らない。<br/>**処理結果：** 接続世代を新しく作り、確認済み初期化を実行してECU応答を検証する。USB接続成功だけでK-Line通信成功にはしない。 |
| OBD-F02 | 取得可能な項目の確認 | **開始条件・入力：** アダプタと実車の応答、確認済みプロトコル情報を受け取る。<br/>**確認・処理：** 許可済みの対応確認要求を有限回送り、SUPPORTED・UNSUPPORTED・UNKNOWNを区別する。一度の無応答を未対応確定にしない。<br/>**処理結果：** 通常取得する項目集合を作り、対応確認結果を通知する。 |
| OBD-F03 | 優先順位付きの定期読取 | **開始条件・入力：** 対応項目、周期、前回取得時刻、車両通信負荷を使う。<br/>**確認・処理：** 車速を優先しつつ、他項目を無期限に待たせない。要求は1件ずつ送り、遅れた周期分をまとめて連続送信しない。<br/>**処理結果：** 次の要求を選び、タイムアウトや負荷増大では取得頻度を下げて通知する。 |
| OBD-F04 | 応答の検査と値の共有 | **開始条件・入力：** 要求に対応した応答、ECU識別、送受信時刻を受け取る。<br/>**確認・処理：** エコー分離、フレーム長・チェックサム・要求との対応を検査し、プロファイルのデータ位置・換算式で内部単位へ変換する。失敗値を0にせず、成功した項目だけ測定参照を更新する。<br/>**処理結果：** 項目別の車両値をUIと利用ソフトへ配信する。 |
| OBD-F05 | 失効と切断からの回復 | **開始条件・入力：** 項目期限切れ、USB抜去、ECU無応答、停止要求を受け取る。<br/>**確認・処理：** 切断では全項目を使用不可にし、個別無応答ではその項目の期限を独立監視する。旧接続の応答を新しい接続へ適用しない。<br/>**処理結果：** 失効理由を通知し、再接続後は対応確認と新規取得から始める。 |

## 3. 内部構成

7モジュールを設ける。USB機器の操作はAdapterConnection、K-Lineの初期化・フレーム送受信はKLineSessionが担当する。ケーブルは本ソフトだけが開き、同時に未完了の診断要求は1件に制限する。利用ソフトが増えても車両への要求数をそのまま増やさず、最新状態を共有する。

| 接続 | 受け渡す情報 |
| --- | --- |
| CapabilityProbe → KLineSession | 実車用プロファイルに登録した確認要求。全アドレス・全サービスを総当たりしない。 |
| PollScheduler → KLineSession | 取得項目ID、期限、対応する許可済み要求定義。 |
| KLineSession ↔ AdapterConnection | USB側の送受信バイトとタイムアウト。ケーブルの電気変換はソフトが代行しない。 |
| KLineSession → ResponseDecoder | エコー分離・フレーム検査後の応答、要求・接続世代・セッション・送受信時刻。 |
| ResponseDecoder → VehicleStateCache | プロファイルの定義で換算した値、単位、出所、時刻品質。 |
| VehicleStateCache → Publisher | 項目別の更新・失効。他項目の観測時刻を一括更新しない。 |

<a id="dd-modules"></a>

### 3.5 モジュール詳細

USB入出力、K-Lineの通信制御、L880Kの項目換算を分ける。検証済みライブラリが利用できる部分は再利用するが、未選定のライブラリが車種固有処理を提供すると仮定しない。

<a id="dd-module-1"></a>

#### 3.5.1 AdapterConnection（USBケーブル接続と転送）

| 項目 | 内容 |
| --- | --- |
| 入力 | 承認済みUSB識別、シリアル設定、送信バイト、読書き期限、必要な線制御。 |
| 出力 | 受信バイト列、実際の送受信結果、接続状態。ECUの値へは換算しない。 |
| 保持情報 | device_identity、port、connection_epoch、read/write期限、ケーブル機能情報。 |
| 処理 | USBシリアルを排他的に取得。短いreadや部分writeを扱い、無期限に待たない。 |
| 関数 | connect_adapter、write_bytes、read_bytes、reconnect_adapter、stop_obd。 |
| 異常時 | USB抜去・I/O例外をKLineSessionへ通知し、全値を無効化。未確認のDTR/RTS/BREAK操作を実行しない。 |

<a id="dd-module-2"></a>

#### 3.5.2 CapabilityProbe（対応項目の確認）

| 項目 | 内容 |
| --- | --- |
| 入力 | 確認済みプロファイルとECU応答 |
| 出力 | 項目別support_stateと確認根拠 |
| 保持情報 | ECU識別、項目別の確認根拠、profile_version、調査回数、確認日時 |
| 処理 | K-Line通信成立後、プロファイルに登録した読取・対応確認だけを行う。標準PID対応ビットマップがあるとは仮定しない。接続機器・ECU変更時は再確認 |
| 関数 | probe_capabilities |
| 異常時 | NO DATAを即UNSUPPORTEDにしない。UNKNOWNとして間隔を空けて確認 |

<a id="dd-module-3"></a>

#### 3.5.3 PollScheduler（読取順序の決定）

| 項目 | 内容 |
| --- | --- |
| 入力 | 対応集合、周期、失敗回数、前回取得 |
| 出力 | 次要求と期限 |
| 保持情報 | next_due、優先度、最終要求、送信予算 |
| 処理 | 優先度と期限で選び、遅い項目も上限待ち時間を設定。滞留周期を再生しない |
| 関数 | select_next_query |
| 異常時 | 長いDTC読取で車速期限が守れなければDTCを延期。負荷上限超過で減速 |

<a id="dd-module-4"></a>

#### 3.5.4 ResponseDecoder（応答検査と単位変換）

| 項目 | 内容 |
| --- | --- |
| 入力 | 検査済みK-Line応答、要求・接続世代・ECU識別、項目の抽出定義 |
| 出力 | VehicleSampleまたは拒否理由 |
| 保持情報 | profile_id/version、データ識別子、応答中の位置・長さ・符号・バイト順・換算式・単位、ECU選択方針 |
| 処理 | 許可したサービス・データ識別子を照合してバイト列から値を抽出。プロファイルの式で内部単位へ換算し、無応答・否定応答・不正値を区別 |
| 関数 | decode_response |
| 異常時 | 複数ECUを平均せず、出所不明はUNKNOWN。例外で全デーモンを止めない |

<a id="dd-module-5"></a>

#### 3.5.5 VehicleStateCache（項目別の値と期限）

| 項目 | 内容 |
| --- | --- |
| 入力 | 検査済み値、失敗、切断、現在時刻 |

### 4.2 取得項目とK-Line要求定義

| 項目 | 論理項目ID | 要求・換算の決定 | 内部単位・扱い |
| --- | --- | --- | --- |
| 車速 | vehicle_speed | L880K用のサービス・識別子・データ位置・係数を確認 | m/s。無応答はnull、0と区別 |
| エンジン回転数 | engine_rpm | 同上 | rpm |
| 冷却水温 | coolant_temperature | 同上 | degC。CPU温度とは別 |
| ECU電圧 | ecu_voltage | ECUの取得可否と換算を確認 | V。測定箇所を明記 |
| 吸気温 | intake_temperature | 取得可否・要求・換算を確認 | degC |
| スロットル開度 | throttle_position | 同上 | % |
| エンジン負荷 | engine_load | ECU算出値の意味を含め確認 | % |
| 燃料残量 | fuel_level | 取得可否・要求・換算を確認 | %。未取得は非表示 |
| 故障コード | diagnostic_codes | L880Kの読取サービスとコード体系を確認 | 読取のみ。標準DTC形式と決めつけない |
| 通信状態 | communication_state | USB接続、K-Line初期化、ECU応答を別管理 | 取得値ではなくサービス状態 |

要求バイト列・識別子・応答オフセット・符号・バイト順・換算式は、すべて対象ECUの確認後に確定する。標準Mode 01のPIDをこの表の既定値にしない。L880Kで標準項目の応答が確認できた場合だけ、そのECU用プロファイルへ登録する。

ケーブル電圧測定はK-Line通信に必須の機能ではないため初期の取得対象にしない。電圧取得機能が別途確認できた場合もECU電圧とは別項目にする。燃費計算は必要な実測項目が未確定のため初期出力に含めない。

<a id="dd-data-contract"></a>

### 4.3 配信データと利用条件

| 項目 | 内容 |
| --- | --- |
| schema_version / source / boot_id / sequence | 共通通知識別子。update・invalidate・statusで単調増加 |
| key / value / unit | vehicle_speed等の項目ID、値、m/s等の単位。無効値はnull |
| support_state | SUPPORTED / UNSUPPORTED / UNKNOWN。取得成否とは別 |
| validity / reason | VALID / DEGRADED / STALE / UNKNOWN / FAULTと理由 |
| sample_id / query_id / connection_epoch | 測定応答と通信の参照。状態再送では新規測定IDを作らない |
| source_service / source_identifier / source_pid / ecu_identity | 実際の要求サービスとデータ識別子・ECU。source_pidは標準PID確認時だけ設定し、それ以外はnull。PIDを仮造しない |
| profile_id / profile_version / session_epoch | 換算根拠とK-Line初期化ごとの世代。別設定・旧セッションの応答を流用しない |
| observed_at_utc / acquired_at_utc | 実測時刻が分かる場合のUTCと、ホスト取得時刻を別項目にする |
| age_ms_at_send / valid_for_ms / time_quality | 測定年齢を評価できる場合の値と期限。時刻品質不明を通知。OBD2サービス側は期限切れ時に`vehicle.invalidate`を送信し、01 カーナビUIも受信値の`valid_for_ms`を100ms周期で監視して表示を消去する |
| query_started_mono / response_received_mono | Pi 5内の要求開始と応答完了。別ホストでは直接引き算しない |
測定時刻が不明な場合のage_ms_at_sendはnullとする拡張案であり、validity=DEGRADEDまたはUNKNOWN、time_quality=UNKNOWNを付ける。利用者は安全判断・位置積分へ採用しない。各ソフトとこの型を契約試験し、nullを0へ変換しない。

01 カーナビUIは、OBD2イベントの`schema_version=1`だけを受け入れる。未対応のスキーマ、スキーマ番号がない構造化イベント、型が不正なスキーマは破棄する。`boot_id`をサービス起動世代、`sequence`をその世代内の通知連番として検査し、同じ世代で連番が前回以下の通知は破棄する。サービス再起動後の新しい`boot_id`は受け入れるが、切り替え前の世代から遅れて届いた通知は破棄する。これにより、再接続前の車速や詳細値が画面へ戻ることを防ぐ。

01 カーナビUIは取得した参考値として表示できるが、03 現在地補正・08 サラウンドビュー・17 ドアロック制御は用途に必要な鮮度・出所が成立する値だけを利用する。

<a id="dd-library"></a>

### 4.4 USB転送方式と読取制限

基本設計は、生バイトのUSBシリアル入出力とK-Line電気変換が可能なケーブルを使い、KLineSessionが対象ECUの通信手順を管理する方式とする。Python側のUSBシリアル転送にはpySerialを候補とする。pySerialには読取・書込タイムアウト、バイト列送受信、BREAK等のAPIがあるが、K-LineやL880K固有診断を自動実装するライブラリではない。[pySerial公式API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html)

python-OBD／ELM327の標準PID取得は本設計の基本経路にしない。ただし、K-Line方式であることだけを理由にELM327型が必ず非対応とは断定しない。ATコマンド型ケーブルと生バイト転送型ケーブルはホスト側操作が異なるため、採用機器がATコマンド型なら別のAdapterConnection実装と通信開始手順を検証し、この生バイト設計へそのまま接続しない。

ケーブルはK-Lineの電圧・送受信・必要な初期化に対応した製品を選ぶ。USB–TTL変換器や端子形状だけ合うケーブルでは代用しない。必要な初期化をUSB側の線制御で生成できない場合、確認済みのケーブル内制御機能等が必要となる。型番未確定のため対応を保証しない。

送信を許可するのは、承認済みの通信開始・必要な通信維持・読取・終了に限る。サービス番号・アドレス・要求バイトをUIから任意指定させない。消去・アクチュエータ操作・書込は許可リストに含めない。

| Capabilities | 対応確認完了時。機器・ECU・接続条件変更で再調査 |
| ActiveQuery | 1件だけ。要求ID、期待応答、開始時刻、期限、connection_epoch、session_epoch |
| KLineSessionState | 初期化状態、通信維持期限、エコー規則、受信バッファ、同期状態 |

<a id="dd-time"></a>

### 5.2 取得時刻と鮮度

多くの診断応答では実センサーの測定時刻そのものを取得できない。応答が届いた時刻を正確な測定時刻と偽らない。要求開始・応答完了・ECU内部更新周期の確認結果を組み合わせて、用途に必要な測定年齢の上限を評価する。

ECUの最大更新遅延を確認できる場合は、保守的な年齢を「確認済みのECU更新遅延上限 + 要求から応答までの時間 + 応答後の経過時間」とする。確認できない場合は時刻品質UNKNOWNとして補正・駐車判断には使わない。

アダプタの応答キャッシュや短縮応答機能で旧値が再生されないことを確認する。新しいquery_idを付けただけで新規測定とは判断しない。車速の応答値は分解能によって細かな移動を表せない可能性もあるため、0の連続応答だけで完全停止を保証しない。

UTC同期なしでもホスト内の要求時間と期限監視は継続できる。時計の不連続・接続再開では旧値を失効させ、03 現在地補正が旧速度で停止時間分を積分しないようにする。

<a id="dd-config"></a>

### 5.3 ポーリングと設定

| 設定 | 方針 |
| --- | --- |
| device_identity / port / cable_backend | 安定したUSB識別、生バイト転送方式とケーブル機能。デバイス番号だけで選ばない。 |
| host_serial / kline_baudrate | USB側のシリアル設定と車体側通信速度を区別。生バイト型で一致が必要な場合も採用ケーブルで確認。値はT.B.D。 |
| protocol_profile / profile_version / ecu_selection | 確認済みL880K用通信定義と対象ECU。未確定なら初期化・読取を開始しない。 |
| init_profile / init_timeout / init_retry_limit | 初期化手順・期待応答・時間条件・試行上限。推測値や総当たりは禁止。 |
| frame_format / checksum / echo_mode | ヘッダ、長さ、終端条件、チェックサム、送信エコーの有無と規則。 |
| request_definitions / decode_definitions | 許可するサービス・データ識別子、応答の位置・長さ・符号・バイト順・係数・オフセット・範囲・単位。 |
| query_timeout / inter_byte_timeout / min_query_gap | 全応答期限・バイト間期限・送信間隔を別管理。受信長上限も有限値。 |
| keepalive_policy / session_timeout | 維持通信が必要かを確認。必要時だけ承認済み要求を他要求と直列化。ACC OFF・停止時は止める。 |
| poll_intervals / value_ttls / request_budget | 車速等の優先順位と期限。K-Lineの通信時間・維持通信を含め実効周期を測る。 |
| timing_profile | ECU更新遅延とキャッシュの条件。未確認なら位置積分や安全判断へ使用不可。 |
| retry_limits / backoff_max / shutdown_timeout | 無応答・再初期化を連発せず、終了も有限期限。 |
| dtc_policy | 許可済み読取だけ。車速期限を妨げる場合は延期。 |
| poll_modes / polling_mode | `minimal`は常時必要な車速・冷却水温など、`full`は車両情報画面表示中だけ取得する詳細項目。UIが画面を離れたらminimalへ戻す。 |

値がT.B.Dのまま診断バイトを送らない。プロファイル変更時は旧値を失効させ、新しいセッションで取得し直す。周期遅延分をまとめて送信せず、受信エラーや負荷増大時は取得頻度を下げて品質を通知する。

取得モードはUIからOBD2専用ソケットへ`set_polling_mode`として要求する。サービスは要求を受理した後、`minimal`または`full`の許可済み項目だけを対象に対応確認と周期読取を行う。UIの車両情報画面を表示していない間は、現在地補正などで必要な最小項目だけを取得し、詳細項目の要求を送信しない。

## 6. 処理・状態遷移



<a id="dd-states"></a>

### 6.1 接続と取得状態

```mermaid
stateDiagram-v2
 [*] --> DISCONNECTED
 DISCONNECTED --> CONNECTING: 承認済みケーブル検出
 CONNECTING --> INITIALIZING: USB接続成功
 INITIALIZING --> PROBING: K-Line通信成立
 INITIALIZING --> RETRY_WAIT: 初期化失敗
 PROBING --> POLLING: 項目確認成功
 PROBING --> DEGRADED: 一部確認不能
 POLLING --> DEGRADED: 項目異常・周期未達
 DEGRADED --> POLLING: 新規応答で回復
 POLLING --> RETRY_WAIT: セッション失効・同期喪失
 PROBING --> RETRY_WAIT: 同期喪失
 DEGRADED --> RETRY_WAIT: セッション失効
 RETRY_WAIT --> INITIALIZING: 間隔・回数・運用許可を確認
 CONNECTING --> DISCONNECTED: USB失敗
 INITIALIZING --> DISCONNECTED: USB抜去
 PROBING --> DISCONNECTED: USB抜去
 POLLING --> DISCONNECTED: USB抜去
 DEGRADED --> DISCONNECTED: USB抜去
 RETRY_WAIT --> DISCONNECTED: USB抜去
 DISCONNECTED --> STOPPING: 停止要求
 CONNECTING --> STOPPING: 停止要求
 INITIALIZING --> STOPPING: 停止要求
 PROBING --> STOPPING: 停止要求

 DEGRADED --> STOPPING: 停止要求

```

K-Line通信が失効した場合はUSB機器が存在していても値を失効させる。INITIALIZINGとPROBINGを通過するまで通常取得を始めない。POLLINGでも個別項目のUNSUPPORTEDやSTALEは残る。

<a id="dd-reconnect"></a>

### 6.2 応答の対応付けと再接続

query_idはホスト内識別子であり、ECUが返すとは限らない。要求を1件ずつ扱い、接続世代・K-Lineセッション・宛先/送信元・応答サービス・データ識別子・長さ・チェックサムをプロファイルに従い確認する。

タイムアウトした要求の遅延応答、送信エコー、初期化応答を次の項目へ適用しない。受信残りを消しただけで同期回復済みとは判断せず、確認済みの同期回復条件を満たさなければセッションを失効させる。再初期化のたびsession_epochを更新する。

USB切断ではconnection_epochも更新し、全項目を使用不可にする。復旧後はK-Line初期化、項目確認、新規読取の順に再開する。UIのDTC読取はcommand_idと期限を検査し、重複・期限切れ要求を遅れて送信しない。

<a id="dd-7"></a>

## 7. 異常処理

| 異常 | 動作 |
| --- | --- |
| 真の0と無応答 | 0は成功値、無応答はNO_DATA。異なる状態として通知 |
| 未対応確定 | 通常ポーリング対象から外す。高速再試行しない |
| 複数ECU・出所不明 | 承認済み選択規則がなければ採用しない |
| チェックサム・長さ・識別子不正 | 応答を拒否。同期不明ならK-Line再初期化。値を更新しない |
| エコー・分割フレーム | ケーブル規則と有限受信領域で組み立て、エコーをECU値にしない |
| 初期化失敗・セッション失効 | 通常読取禁止、値失効、間隔・回数制限付きの再初期化 |
| 単位・換算式・値不正 | 該当項目を拒否。プロファイルを推測で補わない |
| 一項目の通信遅延 | 他項目の時刻を更新せず、周期と期限を再評価 |
| USB抜去・アダプタ故障 | 全項目無効、旧接続破棄、上限付き再接続 |
| 未許可コマンド要求 | 送信前に拒否し、制御や消去は実行しない |
| 終了要求後の応答 | 新しい有効値として配信しない |

<a id="dd-8"></a>

## 8. 起動・終了・運用設計

`python src/raspberry_pi5/obd2_service.py --config src/raspberry_pi5/config/obd2.example.toml --dry-run`で設定検査を行う。実車では`l880k-obd2.service`として常駐させ、開発用Debian起動スクリプトではWaydroid管理とは別プロセスで起動する。実車運用は、設定検査と模擬応答試験を通したL880K用プロファイルで起動する。USBを開いた後にK-Line初期化と対象ECUの応答確認を行う。通常ユーザーに必要なUSBシリアルアクセスだけを与え、他ソフトとの同時利用を禁止する。

利用許可はサービス運用・電源管理と連動する。ACC OFF後の終了猶予中も診断要求を出し続けないよう、OS停止だけでなく診断停止の通知経路を確定する。Pi 5に新しいACC GPIOがあるとは仮定しない。

停止時は新規読取と通信維持要求を止め、状態を無効化する。確認済みの終了手順が必要なら有限期限内で実施し、線制御を適切な非動作状態に戻してUSBを閉じる。USBを閉じることはアダプタの車体側給電停止を意味しないため、常時給電時の待機電流はハードウェア側でも確認する。生通信ログには識別情報が含まれ得るので、公開Gitには模擬応答だけを置く。

<a id="dd-integration-tests"></a>

### 9.2 実車適合と計測

対象車の年式・ECU、ケーブル型番・USBチップ・ドライバ、K-Lineの初期化方式・速度・波形、応答フレーム、エコー、要求項目と換算根拠を記録する。USB側のAPI呼出し成功だけで車体側の初期化成立としない。

公開されたL880K所有者の実装報告ではKWP通信と車速・回転数・水温等の取得例がある。ただし使用機器はELM327系であり、本設計のUSB生バイトケーブルや対象年式・ECUの動作保証にはならない。KWP系を検証候補とし、初期化・データ定義は実機確認までT.B.Dとする。[実装者によるL880K診断アプリの報告](https://devblog.lac.co.jp/entry/20241216)

模擬通信・車体を外した電気確認の後、停車中に既知の少数読取から確認する。実効周期、応答時間、ECU更新遅延、無応答率、値の分解能と計器との差を測定し、取得できない項目を明示する。未知アドレスの総当たり、走行中の画面操作・デバッグは行わない。共通基盤の単体試験は実装済み、実車適合試験は未実施。

## 用語の注釈

| 用語 | 意味 |
| --- | --- |
| K-Line | 車体側の診断通信線・電気方式。本設計ではUSB–OBD変換ケーブル経由で扱う |
| KWP | K-Line上で使われる診断プロトコルの一例。対象ECUへの適合は別途確認 |
| プロファイル | 対象車両・ECU・ケーブルの初期化、要求、応答形式、換算式をまとめた確認済み設定 |
| エコー | 送信したバイトが自分の受信側へ戻ること。ECUの応答と区別する |
| PID / データ識別子 | 診断サービス内の情報を識別する番号。車種固有の識別子を標準PIDと同一視しない |
| ECU | 車両内の電子制御装置。複数から応答する場合がある |
| DTC | 車両が記録する故障コード。本ソフトは読取だけ |
| ポーリング | 決めた周期で値を読み出す要求を送ること |
| UNSUPPORTED / UNKNOWN | 非対応を確認済みの状態と、対応可否がまだ不明な状態 |
